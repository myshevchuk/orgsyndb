# OrgSynDB

OrgSynDB is a local, in-house website for curated synthetic procedures,
modelled on *Organic Syntheses*. Each procedure lives in one source file:
the owner writes Org files, and co-workers can write Markdown files. The
build treats both formats alike.

The procedure site is static. Viewing it loads no fonts, analytics, or other
resources from the internet. It has a light and dark theme, a procedure
catalogue with full-text search and filters, browse directories, and an A4
print layout. Its interface is German by default and can be switched to
English.

The browser layout is optimized for desktop work: catalogue filters in a
sidebar beside a table that fills the available width, recently updated
procedures beside the browse links, and procedure details in a margin
beside the readable procedure text. Narrow windows stack these panels and
put catalogue filters behind a **Filters** button; printing uses the
separate single-column A4 layout.

## Application and collections

This repository is the application: the build program, the validator, the
procedure and sequence schemas, the theme, the lab application
and the tests. The lab application in `webapp/` uses Django, a Python web
framework, to track synthesis tasks and the end-product inventory at
`/lab/` beside the static site. The inventory counts containers ready to
deliver, records deliveries and tracks bulk material available for filling.
See [Container deployment](#container-deployment) to run both.

The repository holds no procedures of its own apart from a demo.
Procedures live in a *collection*,
a separate directory, normally its own Git repository, that the application
builds:

```text
my-procedures/
  orgsyndb.toml        format = 1; registry source and procedure fields
  org/procedures/      Org procedures, OSDB-NNNN-<slug>.org
  md/procedures/       Markdown procedures, OSDB-NNNN-<slug>.md
  md/sequences/        synthesis sequences, SEQ-NNNN-<slug>.md
  static/structures/   compound structure images and procedure scheme images
  build/ public/ pdf/  generated by the build; ignored by Git
```

Keeping the two apart lets the application be developed in the open while
the procedures stay in a private repository. Every file a build generates
goes into the collection. The application's checkout receives only its two
caches of fetched tools, `.emacs-batch/` and `.tools/`.

[`examples/demo/`](examples/demo/) is a complete collection with nine sample
procedures in English, each with a German translation. It shows the layout, and
the tests build it. OSDB-0009 is a general procedure for reducing three aryl
methyl ketones with sodium borohydride. Its first entry makes the same alcohol
as OSDB-0005, so that compound page lists two routes. The demo also has two
sequences, each with a German translation:

- SEQ-0001, “Aspirin from oil of wintergreen”: OSDB-0001 → OSDB-0002,
  with an overall yield of 60 %.
- SEQ-0002, “1-(Biphenyl-4-yl)ethanol from 4′-bromoacetophenone”:
  OSDB-0004 → entry 1 of OSDB-0009, with an overall yield of 77 %.

The demo names [`webapp/demo/registry.json`](webapp/demo/registry.json)
as its registry with `registry = "../../webapp/demo/registry.json"` in
`orgsyndb.toml`. This snapshot, a saved copy of the lab application's
registry, lets you build the demo without running the lab application.
The collection contains procedures and images; its compounds,
vocabularies and author accounts come from the snapshot. The nine
procedures credit the demo's five accounts: `klehmann`, `tbauer`,
`aschmidt`, `jkoch` and `mwolf`.

The registry has 21 substances. Its chemical-class vocabulary has 13 values
on three levels, and every substance has at least one chemical class and a
group. The site shows four built-in fields: `article_number`, `short_name`,
`chemical_class` and `group`. The compound directory shows article numbers
and chemical classes as columns, with an empty article-number cell for a
substance without one. You can filter by chemical class and group, and
search by article number or short name as well as chemical data. Article
numbers and short names follow compound links, for example **Acetic
anhydride (Ac2O)** or **Acetylsalicylic acid (CH-0010, ASA)**. The group
field divides the directory into **Purchased** and **Synthesised** tab
pages, listing ten and eleven substances respectively.

The demo declares four procedure fields: `notebook` (a unique lab-notebook
reference), `project` (a choice), `working_time` (hours, at least zero), and
`inert_atmosphere` (a boolean). Its
`projects` vocabulary in the registry groups
first-year and advanced practicals under **Teaching**, and biaryls and
cinnamates under **Research**. Every demo procedure sets `notebook` and
`project` in both languages; most set `working_time`, and some set
`inert_atmosphere`. All four fields are optional for a new procedure, but a
notebook reference must be unused. Procedure pages show these values, and the
catalogues offer **Project** and **Inert atmosphere** filters.

You can explore the same collection on the [live demo site](https://myshevchuk.github.io/orgsyndb/).

`orgsyndb.toml` must contain `format = 1`, with the number written as an
integer. It also names `registry`, unless you set `ORGSYNDB_REGISTRY` in the
environment, and may declare procedure fields under `[[fields.procedure]]`.
Only `format`, `registry` and `fields` are allowed at the top level.
A choice field's `vocabulary` names one of the registry's four vocabularies:
`chemical-classes`, `inventory-groups`, `projects` or `reaction-types`.
The [field reference](docs/SCHEMA.md#procedure-field-declarations) gives the
procedure rules. The format number is the version of the collection layout;
an application that does not know it refuses the collection instead of
misreading it. The build program checks the file's TOML, format and
top-level keys; the validator checks the procedure declarations against the
registry's vocabularies. Commands such as `clean` and `new` therefore still
work while a declaration needs correcting.

## Install the dependencies

OrgSynDB uses ordinary packages available on all major Linux distributions
and many other Unix-like systems. On Fedora, install the packages required
for every collection with:

```sh
sudo dnf install python3 hugo weasyprint
```

If the collection contains Org procedures, exporting them also requires
Emacs 29.1 or later and Git:

```sh
sudo dnf install emacs git
```

On Debian or Ubuntu, install the packages required for every collection
with:

```sh
sudo apt install python3 hugo weasyprint
```

For Org procedures, also install Emacs and Git:

```sh
sudo apt install emacs-nox git
```

On other systems, install the same tools with your package manager. The
project is tested with Python 3.14, Hugo 0.162.1, and WeasyPrint 70.0. An
older distribution release may package older versions.

A collection that contains only Markdown procedures needs neither Emacs nor
Git.

The build program `tools/orgsyndb` is a Python 3.14 script that uses only
the standard library, so there is nothing to install with pip. You do not
need Node. Caddy is optional and is used only by the deployment example.

Run the program by its path, or put it on your `PATH` with a symlink:

```sh
ln -s "$PWD/tools/orgsyndb" ~/.local/bin/orgsyndb
```

The commands below assume the symlink; otherwise write `tools/orgsyndb`
from the application's directory.

On the first export of an Org procedure, OrgSynDB clones ox-hugo and tomelr
with Git at pinned commits into the application's `.emacs-batch/elpa/`. On
the first build, it fetches Pagefind 1.5.2 into `.tools/` and verifies its
SHA-256 checksum. Each first use needs network access. A Markdown-only build
does not fetch the Org export tools or start Emacs. These tools do not write
to your Emacs configuration.

Check the current machine before building:

```sh
orgsyndb check-deps
```

The command reports each installed or missing required tool. It reports
Emacs, Git, and Caddy separately as optional. If required tools are
missing, its final line names only those tools, for example
`install with your package manager: hugo weasyprint`. It never runs `sudo`
itself.

A machine with all required tools and both downloaded caches reports:

```text
ok      python3
ok      hugo
ok      weasyprint
optional emacs (installed; only for Org procedures)
optional git (installed; only for Org procedures)
optional caddy (not installed; only for deploy/Caddyfile.example)
auto    pagefind 1.5.2 (cached in .tools/)
auto    ox-hugo/tomelr (cached in .emacs-batch/)
```

## Quick start

Build and preview the demo collection:

```sh
orgsyndb -C examples/demo serve
```

Then open <http://127.0.0.1:8000/>. Press `Ctrl-C` to stop the server.

Create your own collection, put it under Git, and add a procedure:

```sh
orgsyndb init ~/my-procedures
cd ~/my-procedures
git init

# Choose one source format. Create the next Org procedure:
orgsyndb new "Ethyl acetate"

# Or create the next Markdown procedure:
orgsyndb new --md "Ethyl acetate"
```

Inside a collection, or any directory below it, every command finds the
collection by itself. Before building, set `registry` in `orgsyndb.toml` to
your lab application's snapshot address or a snapshot file; `init` includes
a commented example. Fill in the procedure stub and find or add its
compounds in the [registry](#compound-registry). From anywhere else, name
the collection with `-C`:

```sh
# Read the registry, export Org and validate procedures and sequences.
# Build the site in public/.
orgsyndb -C ~/my-procedures build

# Build and preview at http://127.0.0.1:8000/.
orgsyndb -C ~/my-procedures serve

# Build and create one A4 PDF per procedure in pdf/.
orgsyndb -C ~/my-procedures pdf
```

A successful build of the demo collection prints these steps:

```text
==> registry: reading ../../webapp/demo/registry.json
==> export: recovering build/export/
==> export: checking org/procedures/ and running ox-hugo
==> export: installing build/export/
==> validate: build/export, md/procedures
validated 22 files: 0 errors, 0 warnings
==> build: staging 9 procedures for locale de
==> build: staging 2 sequences
==> build: staging 8 help pages from docs/
==> build: staging 21 compounds from the registry
==> build: hugo
==> build: pagefind
```

The preview server listens only on `127.0.0.1`, so other machines cannot
reach it. Use `serve --port N` to choose another port. The preview does not
reload after an edit; stop it and run `serve` again. The server tells the
browser to revalidate every file, so the next page load shows the new
build.

`new` selects the next free `OSDB-NNNN` identifier across the Org sources,
Markdown sources, exports, and available Git history of the collection. It
fills the file name, slug, title, and current Europe/Berlin timestamps. New
stubs record no AI model. To record an assisting model, add it by hand as
`#+AI_MODEL: example-model-1` in Org or `ai_model = "example-model-1"` in
Markdown. Add `--lang de` for a German stub; see [Languages](#languages).

## Compound registry

Create and edit substances and vocabulary terms in the lab application's
[substance registry](#substance-registry) at `/lab/registry/`. Procedures
and sequences refer to substances by key, so several procedures and their
translations share the same chemical data. A key uses lowercase letters
and digits joined by single hyphens, for example `ethyl-acetate`. Reuse
that key whenever you mean the same substance; structures are not compared
to establish identity.

Name the registry in the collection's `orgsyndb.toml`:

```toml
format = 1
registry = "http://localhost:8000/lab/registry/snapshot.json"
```

Use the snapshot address of your lab application, beginning with `http://`
or `https://`, or the path of a saved snapshot file. A relative path is
relative to the collection; an absolute path is also accepted. A non-empty
`ORGSYNDB_REGISTRY` environment variable takes the place of the configured
source. A missing source, or a `registry` value that is not a non-empty
string, is a configuration error naming `registry`.

`orgsyndb validate`, `build`, `serve`, `pdf` and `index` read this snapshot.
An address is requested with a 30-second timeout. Except for `index`, which
writes nothing, the tools keep the snapshot they read in
`build/registry.json` and its source in `build/registry.source`. If the
address fails or returns something other than a snapshot, they use the
kept copy only when its source names the same address. The warning names
the address, reason and copy's digest, a fingerprint of the registry's
contents:

```text
orgsyndb: warning: cannot read the registry: <address>: <reason>; using the copy in build/registry.json, digest <digest>
```

Without a copy from that address, the command fails with an error naming
the address. A snapshot file that cannot be read also stops the command.

The site shows these four registry fields in this order. Their
presentation is fixed for every collection.

| Field | Value | English / German label | Where it appears |
|---|---|---|---|
| `article_number` | Article number, as text | Article no. / Artikelnr. | Directory column, search, beside compound links |
| `short_name` | Short name, as text | Short name / Kurzname | Search, beside compound links |
| `chemical_class` | Chemical classes, in the substance's order | Chemical class / Stoffklasse | Directory column and filter |
| `group` | One group | Group / Gruppe | Filter and tab pages |

Chemical classes come from the registry's `chemical-classes` vocabulary;
groups come from `inventory-groups`. A vocabulary is a list of allowed
terms with labels, optionally arranged under parent terms. Tab pages live
at `/compounds/group/<value>/`. The key `group` is reserved for this
directory and cannot be a substance key. The validator reports that
collision on the registry file under `substances`.

Compound pages show each field the substance has, after its chemical
facts. The directory adds article number and chemical class after CAS,
with empty cells for missing values. Labels follow the site's language,
falling back to English where no German label is given. Pages show a
class's full path, such as **Carbonyl compounds › Carboxylic acid
derivatives › Esters**; the directory shows only **Esters**. Several
classes appear in the substance's order, separated by commas.

The article number and short name, when present, follow compound links
in muted parentheses, in that order and separated by `, `. This applies to
the metadata panel, general-procedure scope tables, sequence schemes,
sequence-directory targets and route trees. A substance with neither
value gets no note. The link text stays the substance's name.

A German site uses the substance's `name_de` when present, otherwise
`name`; an English site uses `name`. Formula, molar mass in g/mol and
SMILES, a text notation for molecular structures, may be absent. Missing
values leave empty directory cells, contribute no search text and appear
as no fact on the compound page. CAS is also shown only when supplied.

Put a compound's structure image at `static/structures/<key>.svg` in the
collection, or use `<key>.png`. The tools prefer SVG when both exist; a
substance without either file has no structure image. The key alone
selects the image, so there is no image-path field to fill in.

A collection keeps procedures, sequences and images; its substances and
vocabularies are supplied by the registry. Compound field declarations
under `[[fields.compound]]` are a configuration error naming
`fields.compound`. Procedure fields remain declared under
`[[fields.procedure]]`, with choice values from the registry. Each
procedure's `reaction_types` names exactly one term from its
`reaction-types` vocabulary.

Procedures name substances by key. For example, the demo's aspirin
procedure contains:

```toml
substrates = ["salicylic-acid", "acetic-anhydride"]
products = [{ compound = "acetylsalicylic-acid", yield_percent = 75 }]
```

A **specific procedure** records one run. Its `products` array is required
and non-empty. Each product
has its own yield from 0 to 100; you may list several products. `substrates` is
optional and names the starting materials. Neither list may repeat a key, and a
starting material may not also be a product. The site derives precursor and
used-in links from these lists, so every route to a starting material appears
without entering procedure IDs. Starting materials need registry entries even
when no procedure makes them. A compound that no procedure names is also
allowed.

When one method covers several substrates, write a **general procedure** with a
non-empty `scope` array. Each entry requires non-empty `substrates` and
`products` with per-product yields. Remove top-level `products` and
`substrates`; keep `scale` for the typical scale. Entries may also set `scale`,
`time` (a number followed by `min`, `h` or `d`), `temperature` (an unquoted
number in °C) and `note`. Entries are numbered from 1 in their order. Duplicate
and product-versus-starting-material checks apply within each entry, so a
compound may be a substrate of one entry and a product of another. The site
derives links and search terms from every entry. Two entries of one
procedure must not have the same substrates and the same product compounds,
regardless of their order or yields.

In Markdown, write `scope` as an array of inline tables, as in
[OSDB-0009](examples/demo/md/procedures/OSDB-0009-benzylic-alcohols.md). In
Org, use a table directly preceded by `#+NAME: scope`, outside blocks. Its
required columns are `substrates`, `products` and `yield_percent`; optional
columns are `scale`, `time`, `temperature` and `note`. After the header and
separator, write one row per entry. Separate compound keys and per-product
yields with spaces, in product order. A decimal comma is allowed in table
numbers; an empty cell leaves the field unset. Export writes `scope` front
matter and removes the table and its name from the body. The [Markdown
guide](docs/AUTHORING.md#write-a-general-procedure) and [Org
guide](docs/AUTHORING-ORG.org) show how to write a general procedure.

Any procedure may set `scheme_image`, for example
`scheme_image = "structures/aryl-ketone-reduction.svg"`. Put the image under
`static/structures/`; the relative path must contain no `..` component, end in
`.svg` or `.png`, and name an existing file. In Org, set it with
`#+HUGO_CUSTOM_FRONT_MATTER: :scheme_image "structures/aryl-ketone-reduction.svg"`.
It replaces product structures in the title block. A general procedure without
a scheme shows the placeholder.

List everyone who wrote the procedure in `authors`, using their lab account
user names, each once, for example `authors = ["klehmann", "aschmidt"]`.
Each account must appear in the collection's registry snapshot; it may be
inactive. `checked_by` remains a free-text list of names.

Before validating a new stub, replace its `a.example` author with your user
name. Replace its `example-compound` product key with
your product's key and add the substance in the lab application if it does
not exist. `new` creates the procedure file only. Chemical data belongs in
the registry and structure images in the collection's `static/structures/`;
the procedure records the products, their yields and the starting materials,
at top level for a specific procedure or in scope entries for a general
procedure. The validator warns `unknown field` for `product`, top-level
`yield_percent`, `precursors` or `structure_image` in a procedure.

## Write a synthesis sequence

A synthesis sequence records the route you run through two or more procedures,
including the chosen entry of a general procedure. The site checks that the
steps connect and calculates the overall yield from their product yields.
The **Routes** tree on a compound page is derived from the collection's
procedures.

Copy [`templates/sequence.md`](templates/sequence.md) into the collection's
`md/sequences/`, named `SEQ-NNNN-short-slug.md`. Choose an unused number from
`0001` to `9999`; replace the template's `SEQ-0000` and `seq-0000` with that
ID and its lowercase form. Sequences are written in Markdown, even in a
collection of Org procedures. `orgsyndb new` creates procedure stubs; copy the
sequence template yourself.

Use lowercase letters, digits and single hyphens in the short slug.

Keep the `+++` lines around its TOML front matter. Set `title` and give `date`
and `lastmod` as unquoted offset datetimes. `lastmod` must not precede `date`. Set `target` to the key of
the final substance in the registry. Replace the template's target and steps
with your route. For example, the demo's second sequence uses:

```toml
target = "1-biphenyl-4-yl-ethanol"
steps = [{ procedure = "OSDB-0004" }, { procedure = "OSDB-0009", product = "1-biphenyl-4-yl-ethanol" }]
```

List at least two steps in execution order. Each `procedure` must exist in the
collection. For a general procedure, set `product` to a compound key made by
exactly one of its scope entries. If that product belongs to several entries,
give `substrates` and `products` instead: both lists must contain the chosen
entry's compound keys in full, in any order, without repeats. Use one form
only. A specific procedure takes none of these three keys. `entry` is not a
step key. Reordering the scope table keeps the step on the same chemistry;
the build determines the entry number for the page and manifest.

Each step after the first must take a product of the previous step as a
starting material. The target must be a product of the last step. For a
general procedure these checks use only the
chosen entry. Do not add `authors`: each step credits its procedure's authors.
Write notes below the closing `+++`, such as which intermediate is dried
before use. Run `orgsyndb validate`, then `orgsyndb serve` to inspect the route.

To translate a sequence, copy it with `.de` or `.en` before `.md`. Keep the
base name, `id`, `slug`, `target` and ordered `steps` the same, including
the order within `substrates` and `products` lists. Translate the
title and notes and set the dates for that version. The build chooses one
variant per ID by the same language rules as procedures. The
[schema reference](docs/SCHEMA.md#synthesis-sequences) gives all field rules.

## Use the site

The built site provides these pages. Buttons and messages are named below
as an English site shows them; the German site, the default, shows the
German equivalents, such as **Kopieren** for **Copy**.

The navigation links **Compounds**, **Sequences**, **Procedures** and **Help**
in that order (**Verbindungen**, **Synthesewege**, **Vorschriften** and
**Hilfe** on a German site). A site built with `ORGSYNDB_LAB=true` puts
**Inventory**, **Planning** and **Tasks** first (**Bestand**, **Planung** and
**Aufgaben**), linking to `/lab/inventory/end-products/`, `/lab/planning/`
and `/lab/tasks/`.

Every page has a search field in the same place in the header. Except
on term pages, `/general-procedures/`, `/compounds/` and its tab pages, its
placeholder is **Product, CAS, SMILES or keyword** and its accessible name is
**Search procedures**.

- `/` opens with **Synthetic procedures** and a short introduction.
  With `ORGSYNDB_LAB=true`, **Lab at a glance** appears below the
  introduction, before **Recently updated**. It embeds the stock bar and
  four figures from `/lab/summary/`. **Open the lab overview** opens
  `/lab/` for the full [lab overview](#lab-overview). On a German site,
  these labels are **Labor auf einen Blick** and **Laborübersicht öffnen**.
  The summary needs no JavaScript; its links open in the whole window.
  Without the lab setting, this section is absent.
  **Recently updated** lists up to five procedures, most recently modified
  first. **All procedures, recently updated first** opens the catalogue
  sorted by modification date. To find procedures awaiting a check, use
  **Not yet checked**: it lists up to five drafts, lowest ID first, with
  their creation dates. **All draft procedures (n)** opens the catalogue
  with the draft status selected; `n` is the total number of drafts. This
  section is absent when there are no drafts. **Browse** links to
  **All procedures**, **Reaction types**, **Tags**, **Authors**, **Compounds**
  and **Sequences**, with counts of procedures, terms in use,
  compounds or published sequences.
- `/procedures/` is the catalogue: search, filter, sort and read details
  in one list. With no query or filters it lists every procedure by ID.
  Its table shows **ID**, **Procedure**, **Reaction type**, **Status**
  and **Modified**; follow an ID or title to read the procedure.
- `/general-procedures/` is the catalogue restricted to general procedures,
  those with `scope`. The line **Only general procedures · Browse all
  procedures** links to the full catalogue. Search and filters stay within
  general procedures. **Kind** is fixed to **General procedure**; **Clear all**
  keeps this restriction. **Browse all procedures** removes it while carrying
  your query, other filters, sort and view.
- `/procedures/osdb-NNNN/` shows one procedure. Its title block opens with the
  ID and status badge above the title. For a checked procedure, the checkers'
  names follow the badge when supplied. **Scale** and **Yield** appear under
  the title, followed by **Print / Save as PDF**. With one product in a
  specific procedure, **Yield** shows its percentage; with several, it shows a
  percentage and compound name for each, in product order. A general procedure
  shows its typical scale and the yield range over all products of all entries,
  `<min>–<max> %`, or one percentage when all yields agree. `scheme_image`
  shows a reaction scheme in place of product structures. Without it, a
  specific procedure shows one structure figure per product whose compound has
  an image. A general procedure without a scheme, or a specific procedure with
  no product image, shows **No structure image** on screen. On a wide screen,
  figures sit to the right, above the details column. In a narrow window they
  follow the print button, before the details. A rule closes the title block.
  The details beside the eight body sections always link the products to their
  compound pages under **Product** or **Products**, including when the name
  equals the title. Formula, molecular weight, CAS when supplied and SMILES
  appear there only for one product; for several, follow the compound links to
  those data. **Authors** links each account's name to
  `/authors/<user name>/`, for example `/authors/klehmann/`. Names appear
  exactly as the account has them. **Starting materials** links the compounds
  in `substrates`. For a general procedure, both lists include all entries,
  each compound once in
  order of first appearance. **Precursors** lists other procedures that make
  one of those starting materials; **Used in** lists procedures that start from
  one of the products. Both lists are derived and ordered by procedure ID,
  considering every scope entry. **Sequences** follows **Used in** when this
  procedure is a step of a sequence; it links those sequences by title, ordered
  by sequence ID. The details do not repeat the ID, scale, yield
  or checkers of a checked procedure; checkers of draft or retired procedures
  appear there when supplied. Follow a reference such as **(Note 2)** in the
  text to jump to that note in **Notes**; the note is highlighted on screen. A
  reference to a missing note stays plain text. A general procedure adds
  **Scope** before **Summary**: one row per entry with **Entry**, **Starting
  materials**, **Products** and **Yield**. Starting materials and products link
  to compound pages; products with images show small structures. **Scale**,
  **Time**, **Temperature** and **Note** columns appear only when some entry
  sets that field; unset values leave empty cells.
- `/reaction_types/`, `/tags/`, and `/authors/` list the terms in each category
  with their procedure counts. The catalogue, `/general-procedures/`, these
  directories and every term page open with a row of tabs: **All procedures**,
  **General procedures**, **Reaction types**, **Tags** and **Authors**.
  **General procedures** (**Allgemeine Vorschriften**) is the second tab. The
  current tab is marked; a term page marks its directory's tab. All these pages
  mark **Procedures** as the current section in the site navigation. Each term
  page is a catalogue limited to that reaction type, tag or author. For
  example, `/reaction_types/esterification/`, `/tags/sample-data/`, and
  `/authors/klehmann/` are term-page URLs. The author directory and author
  pages show account names. Search and filters stay within
  that term. The line stating the term restriction links only to **Browse all
  procedures**, which removes the restriction and carries your query, other
  filters, sort and view to `/procedures/`. You can reach the directories from
  the tabs, the home page's **Browse** links or the catalogue filters. On a
  term page, use its directory's tab to return to the directory. Procedure
  metadata links to the term pages.
- `/compounds/` is a searchable, filterable catalogue of every registry entry,
  including compounds no procedure names, ordered by its name in the site's
  language. The table shows the linked name, formula, molecular weight, CAS,
  article number and chemical classes, with empty cells for missing values,
  and counts of published procedures that make it and that use it as a
  starting material. Each general procedure counts once, considering
  all its entries.

  The directory and its tab pages begin with a row of group tabs, styled
  like the procedure tabs. **All compounds** links to `/compounds/`. It is
  followed by one tab per top-level group used by a substance, directly or
  through a group filed under it, labelled with the term's label. Sibling
  terms are ordered by key. The current page's tab is marked.

  Each tab page at `/compounds/group/<value>/` uses the group's label as
  its heading and title. It lists substances in that group or a group filed
  under it, in name order, with its own count, filters and search. The demo
  has `/compounds/group/purchased/` and `/compounds/group/synthesised/`.
  On a tab page, the group filter leaves out the tab's own group and moves
  the groups below it up one level. Filters with no values to list are
  omitted. The header search is labelled **Search compounds: \<label\>**
  and works within that tab. Tab links carry no query or filters. Without
  JavaScript, a tab page shows its whole list.

  **Filters** offers **Chemical class** and **Group**, in that order.
  Each filter shows terms used by substances and their ancestors as an
  indented tree. Each parent is followed by the terms filed under it,
  recursively, with siblings ordered by key. Selecting **Carbonyl compounds**
  also selects compounds filed under ketones and esters. Selections within
  one filter combine with OR; different filters combine with AND.
  Each value's count includes the search and every other filter, excluding
  its own filter's selections. Selected values appear as small buttons
  (chips) that remove a selection. **Clear all** clears the query and
  selections. The count shows the total, or **{shown} of {total} compounds**
  while filtering. A tab page with no filter values has no filter column;
  the count and search remain.

  The header search is labelled **Search compounds**, with the placeholder
  **Name, formula, CAS or SMILES**. It matches English and German names,
  formula, CAS number, SMILES, article numbers and short names where
  supplied. Each query word must match a substring; matching ignores
  case and characters other than letters and digits. For example, `50-78-2`,
  `salicyl` and `c1ccccc1O` work. This search runs in the page without the
  Pagefind index. Rows keep their name order while searching or filtering.

  The address preserves the query and filters, for example
  `/compounds/?q=ester&chemical_class=esters&group=reagents`. Parameters the
  page cannot apply are named in a notice and removed from the address.
  Search and filters need JavaScript; without it, the complete table remains
  visible with a note explaining this.
- `/compounds/<key>/` shows the compound's name, its structure image when
  found by key, and the chemical facts and registry fields it has. SMILES
  has a **Copy** button. **Made by** lists procedures with their yields and
  status; **Used in** lists
  procedures with status. A general procedure appears in **Made by** once per
  entry that makes the compound, as
  `<ID> <title> · entry <n> · <yield> % · <status>`, and in **Used in** once.
  Both lists are ordered by procedure ID and appear only when there are
  matching procedures. **Sequences** follows **Used in** when any sequence
  names this compound as its target; it links those sequences by title, ordered
  by sequence ID. Compound pages mark **Compounds** as the current section.

  **Routes** is the page's last section, after **Sequences** when present.
  It shows ways to make the compound from the collection's published
  procedures, each step with its starting materials. It appears only when
  a route goes beyond one step; otherwise **Made by** already covers it.
  Read the nested lists as alternatives under each compound and required
  starting materials under each step. Those compounds link to their own
  pages, followed by their article number and short name when present,
  and have their own steps below them. Each step shows the procedure's ID and title, entry
  number when needed, yield and status, as in **Made by**. Steps follow
  procedure ID and then entry order. All published procedures take part,
  whatever their status. A general procedure's entry uses only its own
  starting materials.

  A step that starts from a compound already above it on the same branch is
  omitted, so cycles are not followed. If all steps would loop back, the
  compound appears without steps and must be obtained another way. The
  display uses a fixed depth limit of 6 steps and a fixed budget of 200
  steps per tree. A larger tree is drawn to the largest depth that fits.
  When more than 200 steps make the compound directly, the tree shows only
  those. A compound cut off by a limit ends with **more steps on its page**;
  follow its link to continue. Routes are derived during the build; you add
  no route data to a procedure or `orgsyndb.toml`. Compound pages remain
  outside the search index, so routes do not change search.

- `/sequences/` lists every published sequence by ID. Each row shows its title
  linked to the sequence page, its target linked to the compound page, the
  number of steps and the overall yield. The directory works without
  JavaScript.
- `/sequences/seq-NNNN/` shows the sequence ID and title, then **Steps** and
  **Overall yield**. A scheme links the first step's starting materials,
  intermediates and target, with structure images found by substance key
  in the collection's `static/structures/`.
  A plus separates the first step's starting materials. Each arrow gives the
  step number, reaction type and yield. In narrow windows the scheme runs down
  the page. The steps list links each procedure by ID and title, adding
  **entry <n>** for a general procedure, then reaction type, yield and status.
  The notes follow. Overall yield multiplies each step's yield of the compound
  carried into the next step and the last step's yield of the target. If
  several products carry on, it uses the first in product order. The result is
  rounded to a whole percent, with halves rounded up. These pages mark
  **Sequences** as the current navigation section. Sequences are absent from
  the search index; reach them through the navigation or their procedure and
  target-compound links.
- `/help/` lists the guides and glossaries from the application's `docs/`
  directory. Each document has a page under `/help/<slug>/`. The index
  prefers the site's language where a document has both versions and links
  the other version as **English** or **Deutsch**. Documents that exist only
  in German remain available on an English site.

To find a procedure, type in the header search field. On `/procedures/`,
`/general-procedures/` and term pages, this is the catalogue's only search
field. Results update as you type; **Search** applies the query immediately. On
`/compounds/` and its tab pages, the field searches compounds as described in
its entry above. On other pages, including individual compound pages, submit
the field to search in `/procedures/`. On a term page, the field searches
only that term's procedures. Its placeholder is **Search these procedures**;
its accessible name identifies the term, for example **Search
procedures with the tag cinnamate**. On `/general-procedures/`, the placeholder
is **Search these procedures** and the accessible name **Search general
procedures**. Full-text search uses the Pagefind index and finds procedures by
ID, every product's name, formula, CAS number (a chemical registry identifier)
and SMILES string (a text notation for a molecular structure), every starting
material's name, author's account name, tag, or word in the procedure text.
SMILES fragments match any product's structure, including products from
every scope entry.
Starting-material terms also include all entries. SMILES searches ignore
punctuation and compare only letters and digits. A fragment may therefore match
more than one compound. Search results contain procedures only; compound and
help pages are not indexed. Clearing the search field returns to browsing with
your filters still applied.

Under **Filters**, each group of checkboxes is a facet: **Reaction type**,
**Kind**, **Status**, declared procedure filters, **Tag** or **Author**.
**Kind** offers **Specific procedure** and **General procedure**; the German
labels are **Art**,
**Einzelvorschrift** and **Allgemeine Vorschrift**. You can select several
values in each group. Values within one facet combine with OR; different facets
combine with AND. For example, selecting two reaction types and the status
**draft** shows draft procedures of either reaction type. Filters also work
with an empty search field. Each value's count includes the query and all other
facets, leaving out that facet's own selections. Unselected values with zero
matches are hidden; selected values stay visible and removable even at zero.
The result count shows how many procedures match. The **Author** facet
shows account names; its values are the accounts' user names.

A boolean or choice procedure field declared with `facet = true` adds a filter
between **Status** and **Tag**, in declaration order. These filters start open
and have no “all values” link. Boolean filters offer **Yes** and **No** only
when a published procedure sets that value. Choice filters show used values
and their parents as an indented tree. Each parent is followed by the
terms filed under it, recursively, with siblings ordered by key. Selecting
a parent also matches procedures filed under its descendants. These filters appear on
`/procedures/`, reaction-type, tag and author pages, and
`/general-procedures/`; every page offers values from the whole collection.
The address records selections under the declared keys, for example
`/procedures/?project=research&inert_atmosphere=true`. Catalogue search also
finds declared values displayed in the procedure's metadata panel.

Click a selection above the results to remove it, or use **Clear all** to
remove the query and all selected filters. **Clear all** keeps your view and
sort, except for **Relevance**. On a term page it also keeps the term
restriction; on `/general-procedures/` it keeps the general-procedure
restriction.

Use **Sort by** to choose **ID**, **Title (A–Z)**, **Created (newest first)**
or **Modified (newest first)**. During a query, **Relevance** is also available
and is the default unless you have chosen another sort. Without a query, the
default is **ID**. Under **View**, choose **Details** to show product names
under **Product** or **Products**; a single name equal to the title is omitted
here. Formula, molecular weight and CAS when supplied appear only for one
product. Yield uses the same percentage or list of percentages and names as the
procedure page, or the yield range for a general procedure. Products include
every scope entry. Details also shows the creation date and the image of the
first product that has one; without an image it shows no placeholder. **Table**
returns to the compact view; both views keep the same matches and order.

To share a catalogue selection, copy its address. It records the query in `q`,
filters in `type`, `kind`, `status`, `tag` and `author` (repeated for multiple
values), and the chosen `sort` and `view`. An `author` value is a user name,
for example `/procedures/?author=klehmann`. Kind values are `specific` and
`general`. On `/general-procedures/`, the kind is fixed by the page and cannot
be changed through the address. Reloading or following a shared link restores
those choices; the browser's Back and Forward buttons restore earlier choices.
Parameters that cannot be applied are reported and removed from the address.

Search needs the site over HTTP, from `orgsyndb serve` or another web
server; it does not work when you open `public/index.html` through a
`file:` URL. If the index cannot be loaded, **Search unavailable** appears.
Use **Show the list without the search** to remove the query and browse
with your filters kept; browsing without a query needs no search index.

Without JavaScript, `/procedures/` lists every procedure by ID, and term pages
list every procedure of their term by ID. `/general-procedures/` lists every
general procedure by ID. A note explains that search, filters and sorting need
JavaScript and links to the reaction-type, tag and author directories. On a
term page or `/general-procedures/`, submitting the header search reloads that
page with the query; elsewhere it leads to the catalogue. In either case, the
static list does not apply the query.

On a procedure or compound page, **Copy** copies the SMILES and briefly
reports **Copied**. Clipboard access needs a secure context: `https:` or
`http://127.0.0.1`. At another address the button selects the SMILES and
reports **Selected: press Ctrl+C** instead.

To see when the site was built, look at the end of any page's footer,
for example `built 2026-10-28 20:08` or `Stand 2026-10-28 20:08` on a
German site. Every page of one build shows the same time.

## Languages

The site has one language, set by `locale` in the application's
`site/hugo.toml`: `"de"` (the default) or `"en"`. It applies to every
collection the application builds. The language decides the interface
text, the reaction-type labels, the compound names, the catalogue's texts,
the PDF page footer and the decimal separator, and it decides which file of a
procedure or sequence is published. The interface strings are in `site/i18n/de.toml`
and `site/i18n/en.toml`. Reaction-type labels come from the registry's
`reaction-types` vocabulary. A German site uses `label_de` when present,
otherwise `label`; an English site uses `label`.

A procedure file's name may carry a language code before its suffix:
`OSDB-0001-x.de.org` or `OSDB-0001-x.en.md`. Files with the same ID are
variants of one procedure. Every procedure is published, once: for each
ID the build takes the file tagged with the site's language if there is
one, else the file without a code, else a file tagged with another
language. With `locale = "de"`, `OSDB-0001-x.de.org` is published in place
of `OSDB-0001-x.org`, while `OSDB-0001-x.en.org` would lose to it. Sequence
variants in `md/sequences/` follow the same selection rules. There is no
language switch on the site.

Procedure variants share their ID, base name and language-neutral facts: `status`,
`reaction_types`, `tags`, `products`, `substrates`, `scope` and `scheme_image`.
Only each scope entry's `note` may be translated; entry order and other scope
values must agree. `orgsyndb validate` reports any difference as an error.
Numeric yields compare by value, so `85` and `85.0` agree. Title, scale,
hazards, references, timestamps and the body are translated freely. Author
lists may differ between variants; each lists lab account user names.
Compound names come from `name` and `name_de` in the shared registry,
independently of the procedure's language.

A procedure may state its language in an optional front-matter field,
`language = "de"` or `"en"`, which must match the file name's code when
both are present. A tagged file gets it on publication. The page marks a
procedure whose language differs from the site's with a `lang` attribute.

German procedures use German section headings, from `Zusammenfassung` to
`Literatur`, and German Reagents columns; the
[procedure schema](docs/SCHEMA.md#languages-and-variants) lists them. A
file without a code may use the English or the German headings. Create a
stub in a given language with:

```sh
orgsyndb new --lang de "Produktname"
orgsyndb new --md --lang de "Produktname"
```

## Print procedures

`orgsyndb pdf` uses WeasyPrint to create A4 PDFs in the collection's
`pdf/`, one per published procedure, named after its file, such as
`pdf/OSDB-0001-salicylic-acid.de.pdf`. These PDFs have the procedure ID
and title in a running header and `Seite N von M`, or `Page N of M` on an
English site, in the footer. Navigation, buttons, and an empty
structure-image placeholder are omitted. The sample-data banner remains. Tables stay within the margins,
numeric columns do not wrap, and table rows and numbered steps stay together
across page breaks.

The first printed page includes its full procedure URL, ID, status, and
last-modified time. The URL begins with `params.siteurl` from
`site/hugo.toml`, which defaults to `http://127.0.0.1:8000`. Set the public
origin for a PDF run with `HUGO_PARAMS_SITEURL`, for example:

```sh
HUGO_PARAMS_SITEURL=https://orgsyndb.example.org orgsyndb pdf
```

The URL is printed as text and is not fetched. The procedure page's
**Print / Save as PDF** button, or the browser's `Ctrl-P` command, uses the
same complete black-on-white A4 layout. Browser support for running headers
and page numbers varies; Firefox prints neither, while WeasyPrint includes
both.

To print the sequence overview itself, use the browser's `Ctrl-P` command on
its page. `orgsyndb pdf` creates PDFs of individual procedures; it does not
combine a sequence and its procedures into one PDF.

## Daily workflow

1. Create a stub with `orgsyndb new "Title"` for Org or add `--md` for
   Markdown.
2. Find or add substances in the lab registry for its products and
   starting materials.
   Fill in its metadata and all eight body sections. For a shared method
   applied to several substrates, use `scope` as described in the authoring
   guides below.
3. Update `#+LAST_MODIFIED` in Org or `lastmod` in Markdown whenever you
   change the procedure.
4. Run `orgsyndb validate`. Fix every error and review every warning.
5. For a route of two or more procedures, copy the sequence template into
   `md/sequences/`, fill its target, steps and notes, then validate again.
6. Run `orgsyndb serve`, then open <http://127.0.0.1:8000/> to inspect the
   built page.
7. Run `orgsyndb pdf` when you need printable A4 files.
8. Commit the procedure, any sequences, structure images and scheme images
   to the collection's repository.

Org files remain the source of truth. Never edit their generated Markdown
copies in `build/export/`.

## Edit in Emacs

The `orgsyndb` package helps you fill in procedure metadata, find compounds,
check your work and preview the page from Emacs. It lives in the
application's `emacs/` directory and needs Emacs 29.1 or later. It requires
no third-party package; Flycheck is optional.

### Install the package

Choose one of these three methods. Replace `~/path/to/orgsyndb` with your
application checkout.

**Load from a checkout.** Add this to your Emacs init file:

```elisp
(add-to-list 'load-path "~/path/to/orgsyndb/emacs")
(require 'orgsyndb)
(global-orgsyndb-mode 1)
```

**Doom Emacs.** Add this to `packages.el`:

```elisp
(package! orgsyndb
  :recipe (:local-repo "~/path/to/orgsyndb" :files ("emacs/*.el")))
```

Add this to `config.el`, then run `doom sync`:

```elisp
(use-package! orgsyndb
  :config (global-orgsyndb-mode 1))
```

**Install from Git.** Use `package-vc-install`:

```elisp
(package-vc-install
 '(orgsyndb :url "https://github.com/myshevchuk/orgsyndb"
            :lisp-dir "emacs"))
```

This installs from the repository's default branch, `main`, which is
stable. To install the newest work, add `:branch "develop"` to the package
specification:

```elisp
(package-vc-install
 '(orgsyndb :url "https://github.com/myshevchuk/orgsyndb"
            :lisp-dir "emacs" :branch "develop"))
```

Then add this to your init file:

```elisp
(require 'orgsyndb)
(global-orgsyndb-mode 1)
```

This method clones the repository into Emacs's package directory. The
package runs `tools/orgsyndb` from that clone. With the checkout methods,
it runs the program from the checkout holding the package. Set
`orgsyndb-program` if you want to use another program.

### Write and check a procedure

`global-orgsyndb-mode` enables `orgsyndb-mode` when you visit a collection's
Org or Markdown procedure, sequence or `orgsyndb.toml`, whatever the major
mode. `OSDB` appears in the mode line. Press `C-c C-;` to open the menu of
twelve commands, or call them with `M-x`.

Use `completion-at-point` to fill in metadata keys and values. In
Markdown procedures, completion works inside the `+++` information block;
in Org, it works on `#+HUGO_CUSTOM_FRONT_MATTER` and `#+HUGO_TAGS` lines
and in the `substrates` and `products` columns of the table named `scope`.
It offers statuses, languages, reaction types, tags, authors, compound
keys, scheme images and the collection's declared choice and boolean
fields. Labels and compound names help you choose. For `authors`, it offers
the registry's account user names, each annotated with the account's name.
For `checked_by`, it offers names already used under that key in procedures;
you can also enter other names. Sequences also offer
procedure IDs and target substance keys. Inside a step's `product` string,
completion offers the named general procedure's products, each once in file
order, annotated with the entry numbers that make it. This works for Markdown
and Org general procedures. Inside a step's `substrates` and `products` lists,
it offers compound keys. A specific procedure offers no `product` candidates;
there is no completion after `entry =`.
Compound keys and vocabulary terms come from the registry through the
index. Completion leaves body text to your other completion functions.

To insert a compound key by its name, use `M-x orgsyndb-insert-compound`;
in `.de` files it offers German names. On a compound key, press `M-.` to
open `*orgsyndb <key>*`. This definition buffer shows the substance's name
and, when present, its German name, formula, molar mass, CAS number,
article number and short name. For a registry at an address, the button
**Open its page in the lab application** opens the substance's page in
your browser. For a file registry, the buffer says `It has no page: the
collection's registry is a file.`

On `OSDB-NNNN` or `SEQ-NNNN`, `M-.` visits the procedure or sequence file,
preferring the current file's language, then the variant without a language
code. Press `M-?` on a key or ID to list mentions in procedures and
sequences, including body text. Eldoc, Emacs's information display at the
cursor, shows a compound's name, formula, molecular weight and CAS number,
or a procedure's title and status. `M-x orgsyndb-structure-mode` opens a
side window with the compound's name, formula and structure image when
available. It finds the image at `static/structures/<key>.svg`, or
`<key>.png` when there is no SVG.

In Org sources, checks of the file name, keywords, timestamps and scope
table show problems as you type. Saving a collection file runs
`orgsyndb validate` for the whole collection in the background. Its
problems appear on the relevant field lines in open collection buffers;
export problems appear on the Org source. If the export stops validation,
Emacs says why and keeps the earlier validation problems. Flymake shows
problems by default. Set `orgsyndb-diagnostics` to `flycheck` to use
Flycheck, or to `nil` to disable both displays. Set
`orgsyndb-validate-on-save` to `nil` to disable validation on save.
`M-x orgsyndb-validate` lists every problem in a compilation buffer;
`M-x next-error` takes you to each field's line.

Saving a procedure or sequence also updates `#+LAST_MODIFIED` or `lastmod`
in Europe/Berlin time, with English weekdays and the appropriate offset.
The mode uses settings local to that buffer, so your `time-stamp` settings
elsewhere stay in force. Set `orgsyndb-update-timestamps` to `nil` to
disable these updates. Collection data is read through `orgsyndb index`
when first needed and refreshed after each save. For changes made outside
Emacs, save a collection file or run `M-x orgsyndb-refresh-index`.

### Create files and preview the result

- `M-x orgsyndb-new-procedure` creates a stub through `orgsyndb new`.
  With `C-u M-x orgsyndb-new-procedure`, choose the format and language.
- `M-x orgsyndb-visit-variant` opens another language variant of the
  procedure or sequence. `M-x orgsyndb-create-translation` creates a
  procedure variant beside the source, keeping its front matter with new
  creation and modification times and replacing the body headings with
  those of the other language. Translate the text in place. The command
  refuses to overwrite an existing file.

Run `M-x orgsyndb-preview` to open the current file's page in your browser.
The first preview starts `orgsyndb serve`; later previews rebuild the
site. The port is `orgsyndb-preview-port`, initially 8000. The site shows
one language; when the page uses another variant, Emacs names it in a
message. `M-x orgsyndb-preview-on-save-mode` rebuilds while the site is
served, after one second without another save by default; adjust
`orgsyndb-preview-delay` to change that interval. Reload the browser page
to see changes. Use `M-x orgsyndb-stop-server` to stop serving, or
`M-x orgsyndb-serve` to start it directly. `M-x orgsyndb-pdf` builds the
PDFs and opens the current procedure's PDF.

The package runs validation, builds, PDFs and the server's first build
one at a time per collection because each rewrites `build/`. Requests
wait for the preceding run. Commands started in a shell are not
coordinated with these runs.

## Command reference

```text
orgsyndb [-C DIR] <subcommand> [options] [arguments]
```

`-C DIR` (or `--collection DIR`) names the collection. Without it, the
program uses the nearest directory, from the working directory upwards,
that holds `orgsyndb.toml`, and fails if there is none. `help`,
`check-deps` and `init` need no collection.
The program finds the application from its own location, following
symlinks, so it works from any directory. In the table, paths without a
prefix are relative to the collection.

| Command | What it does |
|---|---|
| `export` | Checks the top-level entries in `org/procedures/`, reports Org file-name, keyword, scope-table and forbidden-route problems on standard output, then exports every `*.org` source into `build/export/` if it finds no error. An Org error stops the export before ox-hugo is fetched and leaves `build/export/` unchanged. When it finds no Org source or reportable entry, it leaves that directory empty and starts no Emacs. |
| `validate` | Reads the registry, then runs `export`. An Org error stops the command there; otherwise the Markdown-only validator checks procedures in `build/export/` and `md/procedures/` and sequences in `md/sequences/` against the snapshot, using the collection's `static/` for scheme images. Errors fail the command; warnings do not. |
| `build` | Reads the registry, runs export and validation, stages the registry's substances and account names for the site, builds into `public/` with Hugo, then indexes it with Pagefind. A validation error stops the command before Hugo. |
| `serve [--port N]` | Runs `build`, then serves `public/` on `http://127.0.0.1:N/` until `Ctrl-C`. The default port is `8000`. |
| `pdf` | Runs `build`, removes the previous `pdf/`, and renders every procedure to `pdf/<source-file-name>.pdf` with WeasyPrint. |
| `new [--md] [--lang LANG] TITLE...` | Creates an Org stub with the next free ID, or a Markdown stub with `--md`. `--lang de` or `--lang en` creates a stub in that language named `<ID>-<slug>.<LANG>.org` or `.md`. It never overwrites an existing file. |
| `init DIR` | Creates an empty collection in `DIR`: `orgsyndb.toml` with a commented registry-address example, a `.gitignore` for the generated directories, and empty `org/procedures/`, `md/procedures/`, `md/sequences/` and `static/structures/` directories. It refuses a directory that already holds `orgsyndb.toml`, and it does not run `git init`. |
| `clean` | Removes `build/`, `public/`, and `pdf/`. |
| `clean --all` | Also removes the application's `.emacs-batch/` and `.tools/`. Their contents are fetched again on the next relevant run. |
| `check-deps` | Reports required tools; optional Emacs, Git, and Caddy; fetched tools; and the missing tool names when a required tool is missing. |
| `index` | Reads the registry and prints the site language, procedure and sequence schema, registry source and digest, four compound fields, procedure declarations, accounts, vocabularies, substances, procedures and sequences as one line of JSON for an editor. Needs a collection but no external tool, takes no arguments and writes nothing. Lists Markdown files it cannot parse with the reason instead of failing. Org procedures are listed by file name only. Exits 1 on a configuration error, including an unreadable registry without a matching kept copy. |
| `manifest` | After a build, prints the site language, published procedures with their author user names in file order and their scope entries, and sequences with their steps as one line of JSON for the lab application's import. Takes no arguments, reads no registry and writes no files. Collections with Org sources need `build/export/`; run `build` first. |
| `help` | Prints the command summary. `-h` and `--help` do the same. |

The program exits 0 on success, 1 on failure, and 2 on a usage error.

For `build`, set the environment variable `ORGSYNDB_LAB=true` to include
the lab application's views in the site's header and its summary on the
home page. It also accepts `1`, `yes` and `on`. Leave it unset or empty,
or set it to `false`, `0`, `no` or `off`, to omit those links and the
summary. Values are case-insensitive. Any other value stops `build` with
exit 1 before export, with a message naming
`ORGSYNDB_LAB` and the value. This also applies to `serve` and `pdf`, which
run `build`. Enable this setting only where the lab application runs under
`/lab/` on the same host, as in the container deployment. A lab build must
be served at the host's root; its lab links and summary do not work under
a path prefix. Leave the variable unset for the GitHub Pages demo and
local `orgsyndb serve` previews, which have no lab application.

The normal `validate` command checks top-level procedure and sequence
files. Subdirectories under `md/procedures/` or `md/sequences/` are invalid.
Product problems use fields such as `products[1].yield_percent`, counting
from 1. The summary counts procedure and sequence files, including all
language variants. Procedure dates do not schedule publication: a valid
procedure with a future date is built immediately.

For a direct validator invocation, `--registry FILE` chooses the snapshot;
it defaults to `build/registry.json` in the working directory. The snapshot
supplies account user names, substance keys, reaction types and the terms of
procedure choice fields. A registry with no reaction-type terms makes every procedure's
reaction type unknown. The lab application checks substance values. The
validator also refuses a substance keyed `group`, which the lab application
does not create, reporting field `substances` on the registry path as
given. Unknown references report:

```text
unknown author "<name>"; the registry has no account of this user name
unknown compound "<key>"; the registry has no substance of this key
unknown reaction type "<value>"; the registry has no such reaction type
unknown value "<value>" of the vocabulary <name>
```

Under `authors`, a repeated user name reports `"<name>" is named twice`.
A value that is not a list of strings reports
`must be a list of user names, e.g. ["a.example"]`; an empty list reports
`must not be empty`. The singular `author` key reports
`use authors, a list of user names`.

`--settings FILE` chooses the collection's `orgsyndb.toml` for a direct
validator invocation. Its declarations check procedures, including Org
exports. It defaults to `orgsyndb.toml` in the working directory; a missing
default declares no extra fields. An explicitly named file must exist.
A declared choice field's `vocabulary` names one of the snapshot's four
vocabularies. `--static-dir DIR` chooses the directory for procedure
scheme images and defaults to `static` in the working directory.

`orgsyndb validate` and `build` pass `--settings orgsyndb.toml
--static-dir static --registry build/registry.json --sequences md/sequences`
and the content roots `build/export` and `md/procedures`, omitting a root
that does not exist. A registry that cannot be read or is not a snapshot,
invalid settings and invalid procedure declarations are configuration
errors. The direct validator exits 2 and writes `validate.py: error: ...`
to standard error with no standard output. The options `--compounds` and
`--vocabulary` are usage errors with exit 2.

The JSON from `orgsyndb index` has the keys `site_language`, `schema`,
`registry`, `fields`, `accounts`, `vocabularies`, `compounds`, `procedures` and
`sequences`. `schema` describes procedures and sequences. `registry`
holds `source` and `digest`; `fields.compound` lists the four built-in
fields and `fields.procedure` the collection's declarations. `accounts`
lists the snapshot's accounts, each with `username` and `name`. Each
`compounds` entry holds `key`, `data` as staged for the site, and `url`.
For an HTTP registry, `url` is
`<origin>/lab/registry/substances/<key>/`, using the registry address's
scheme, host and port; for a file registry it is `null`.

General-procedure fields use `scope[n].<key>` and `scope[n].products[m].<key>`,
with indices starting at 1. An empty `scope` reports `must not be empty`;
top-level `products` or `substrates` report
`a general procedure lists them in scope; move <key> into its entries`. Time
and temperature errors explain the required units or numeric form. Under
`scope[n]`, `has the same substrates and products as entry <m>` means two
entries name the same chemistry; keep only one such entry. Malformed
Org scope tables report field `scope` and stop export before Markdown
validation. The [schema reference](docs/SCHEMA.md#org-scope-table) lists each
table error and its correction.

Sequence fields use `steps[n].procedure`, `steps[n].product`,
`steps[n].substrates` and `steps[n].products`, counting from 1. A missing entry
choice reports `name its entry by a product: <keys>` under `product`. If the
message names several entries for that product, give the entry's complete
`substrates` and `products` lists instead. `steps[n].entry` reports
`not a key of a step; name the entry by its product`.
A missing procedure reports `<id> not found in any content root`; a broken
chain reports `starts from none of the products of step <k>` under the next
step. A wrong target reports `is not a product of the last step`. For a direct
validator invocation, `--sequences DIR` selects the sequence directory and
defaults to `md/sequences` in the working directory. A missing directory holds
no sequences; an existing path that is not a directory is a configuration
error. `orgsyndb validate` passes `--sequences md/sequences`. The
[schema reference](docs/SCHEMA.md#sequence-messages) lists sequence messages
and corrections.

|---|---|

## Generated directories

These directories are generated and must not be committed. The collection's
`.gitignore`, written by `init`, ignores its three.

| Directory | Where | Contents |
|---|---|---|
| `build/` | collection | The snapshot last read in `registry.json` and its source in `registry.source`, Org exports, selected procedure and sequence variants under `content/`, one JSON file per substance in `data/compounds/`, registry fields and procedure declarations with display and filter settings and vocabulary labels, paths, ancestors and tree order in `data/fields.json`, reaction-type labels in `data/reaction_types.json`, account user names mapped to their names in `data/authors.json`, derived routes in `data/routes.json`, the generated Hugo configuration overlay, Hugo's resource cache, temporary export data, and `export.log`. |
| `public/` | collection | The complete static website and Pagefind index. |
| `pdf/` | collection | One generated PDF per procedure. |
| `.emacs-batch/` | application | The application's own ox-hugo and tomelr installations. |
| `.tools/` | application | The verified Pagefind binary. |

The build passes Hugo a configuration overlay, `build/hugo-config/`, that
mounts the collection's sources and static files into the application's
site, mounts `build/data/compounds/` as `data/compounds` and the selected
sequence variants from `build/content/sequences/` as sequence pages, and
sets the output directories.

Each `build/data/compounds/<key>.json` holds the substance's `name`,
`name_de`, `formula`, `mw`, `smiles`, `cas` and four registry fields where
present. `chemical_class` is a list of keys. When an image exists, the file
also holds `structure_image` as `structures/<key>.svg` or `.png`.

Before Hugo runs, the build writes `build/data/fields.json` with labels in
the site's language, under `compound` and `procedure`. Every field has `key`,
`type` and `label`; boolean and choice fields also have `facet`, numbers
with a unit have `unit`, and choices have `multiple`, `values` and `order`.
Registry fields also have `column`. Text registry fields have `search`
and `beside`; choice registry fields have `tabs`. Procedure fields have
none of those four keys. Each choice value has its label, its label `path`
and `ancestors` (the keys of its ancestors). The vocabulary's `order` lists
each parent followed by the terms filed under it, recursively, with
siblings ordered by key. The overlay mounts `build/data/` as collection
data, available to the theme as
`site.Data.collection.fields`. The build also writes
`build/data/reaction_types.json`, with each reaction-type slug mapped to its
`label` in the site's language. The theme reads these labels as
`site.Data.collection.reaction_types`.

Before Hugo runs, the build also writes `build/data/routes.json`. For each
compound with a route beyond one step, it holds a list of steps. Each step
has `procedure`, `yield_percent` and `substrates`, with `entry` only for an
entry of a general procedure. Each substrate has `compound`, its own
`steps` list (empty unless drawn), and `more`, which is true when a limit
cuts it off. The theme reads this data as `site.Data.collection.routes`.

It runs Hugo without a build lock, so nothing is written under the
application's `site/`.

### Lab application tests and local server

The lab application has its own dependencies in `webapp/pyproject.toml`
and `webapp/uv.lock`. With Python 3.14 or later and uv, the Python project
manager, run its tests separately:

```sh
cd webapp
uv run pytest
```

The suite uses SQLite, a database stored in one file, by default. Set
`ORGSYNDB_DATABASE_URL` to run it against PostgreSQL instead. The
[`webapp.yml`](.github/workflows/webapp.yml) GitHub Actions workflow runs
this suite on SQLite and on a PostgreSQL 18 service on pushes to `main`
and `develop`, and on pull requests.

The standalone [database diagram](webapp/docs/database-schema.html) shows
the lab application's tables and their relationships, generated from the
models. The suite runs `schema_diagram --check`, so a model change that
leaves the file out of date fails `uv run pytest`. Regenerate it from
`webapp/` with the command below and commit the file. Add `--check` to
check without writing; it exits 1 if the file is missing or out of date.
Use `--output PATH` to write or check another file. To move a table in the
diagram, edit `GRID` in `webapp/orgsyndb_web/schema_diagram.py` before
regenerating.

```sh
ORGSYNDB_DEBUG=true uv run python manage.py schema_diagram
```

To start the local lab server, run from the repository root:

```sh
cd webapp
export ORGSYNDB_DEBUG=true
uv run python manage.py migrate
uv run python manage.py runserver
```

Open <http://127.0.0.1:8000/lab/>. The local database is
`webapp/db.sqlite3` unless you set `ORGSYNDB_DATABASE_URL`.
The interface uses the latest accepted collection import's language,
German or English. It uses German until an import is accepted. See
[Inspect collection imports](#inspect-collection-imports) for the records
the application reads from a collection. Add substances in the
[lab registry](#substance-registry), or use `registry_load` to fill an
empty registry from a snapshot. Substance names, molar masses and article
numbers come from that registry.

To try the lab with invented records, use a separate SQLite file. The
demo runs without building a collection. From the repository root:

```sh
cd webapp
export ORGSYNDB_DEBUG=true
export ORGSYNDB_DEMO=true
export ORGSYNDB_DATABASE_URL=sqlite:////tmp/orgsyndb-demo.sqlite3
uv run python manage.py migrate
uv run python manage.py demo_data
uv run python manage.py runserver
```

This keeps the demo apart from `webapp/db.sqlite3`. The command loads
`webapp/demo/registry.json`, then writes inventory and task records dated
back from today in Europe/Berlin. For example, a successful run prints:

```text
Demo data as of 2026-11-07 written: 5 accounts, 21 substances, 17 items, 234 delivery notes and 21 tasks.
```

The date and counts depend on the day you run it. Open
<http://127.0.0.1:8000/lab/> and use the accounts listed under
[Demo deployment](#demo-deployment). To renew an existing demo, run
`uv run python manage.py demo_data --replace` from `webapp/`; this deletes
changes you made while trying it, including substances and vocabulary
terms. Without `--replace`, the command refuses a database that already
holds lab records, including accounts or a registry.

## Optional validation before commits

The application includes `tools/hooks/pre-commit`, an optional Git hook for
a collection's repository. A hook is a command that Git runs automatically
at a particular point. This one runs `orgsyndb validate` before every
commit on each collection in the repository and refuses the commit if
validation finds an error.

Enable it in the collection's repository with:

```sh
git config core.hooksPath /path/to/orgsyndb/tools/hooks
```

Alternatively, link the supplied hook into Git's default hook directory:

```sh
ln -s /path/to/orgsyndb/tools/hooks/pre-commit .git/hooks/pre-commit
```

Replace `/path/to/orgsyndb` with the application's directory. Nothing
enables the hook automatically. It validates files as they exist in the
working tree, including changes that are not staged, and it adds the normal
export time to every commit. It validates the collection at the top of the
repository and every collection whose `orgsyndb.toml` is tracked or staged,
so a collection may also live in a subdirectory. In a repository without a
collection it lets the commit through.

## Container deployment

`deploy/` runs OrgSynDB on a server with Docker Compose or Podman Compose.
Five services build and serve the site and keep the lab's records:

- `builder` clones the collection from its Git repository, builds the site
  inside the container, and checks for new commits every five minutes. It
  also follows the application's own repository, so the server picks up
  new versions of the static site by itself. It reports each build to the
  lab application and publishes only a release the application accepts.
- `web` serves the last published site with Caddy on port 8080 and
  forwards `/lab/` to `app`, except the builder's manifest path. Caddy
  answers 404 for every path beginning with `/lab/collection/manifest`;
  the builder sends manifests directly to `app` over the Compose network.
- `db` runs PostgreSQL 18 and keeps the lab's records in the `db` volume.
- `app` runs the lab application, built from the checkout that holds
  `deploy/compose.yaml`. It stores accepted collection imports in the
  database.
- `backup` dumps the database daily into `deploy/backups/` on the host.

`builder` and `web` share one image. They and `app` share the `data`
volume; `web` and `app` read it without writing to it.

The collection's repository may be anywhere Git reaches: an `https://` or
`ssh://` URL on the internet or the intranet, or a repository on the
server itself mounted into the container. Building the image needs
internet access, since it installs Fedora packages and fetches ox-hugo,
tomelr and Pagefind into the image. Once built, the containers need access
only to the two repositories; with application updates off, only to the
collection's.

### Set up the services

From a checkout of the application, copy the example settings:

```sh
cd deploy
cp orgsyndb.env.example orgsyndb.env
```

In `orgsyndb.env`, set `ORGSYNDB_COLLECTION_REPO` and choose the database
user, password and name in `POSTGRES_USER`, `POSTGRES_PASSWORD` and
`POSTGRES_DB`. Repeat those values in `ORGSYNDB_DATABASE_URL` as
`postgres://<user>:<password>@db:5432/<database>`; the password appears
in both settings. Set `ORGSYNDB_ALLOWED_HOSTS` to the host names you use
to reach the site, separated by commas.

Generate a secret key for sign-ins and put the result in
`ORGSYNDB_SECRET_KEY`:

```sh
python3 -c 'import secrets; print(secrets.token_urlsafe(50))'
```

Generate a separate service token and put it in `ORGSYNDB_BUILDER_TOKEN`:

```sh
python3 -c 'import secrets; print(secrets.token_urlsafe(32))'
```

The builder uses this token to authenticate each build report, called a
**manifest**, and the app accepts only that token. Both services read it
from `orgsyndb.env`. Without it, the builder builds nothing and the app's
manifest endpoint answers 404. `ORGSYNDB_MANIFEST_URL` defaults to
`http://app:8000/lab/collection/manifest/` on the Compose network.

Git ignores `deploy/orgsyndb.env` and `deploy/backups/`. After filling in
the settings, start the services from `deploy/`:

```sh
docker compose up -d --build
docker compose logs -f builder
```

The site is then at `http://<server>:8080/`, with the lab application at
`http://<server>:8080/lab/`. Until the app accepts the first site build
and the builder publishes it, the static site answers 404.

[`deploy/orgsyndb.env.example`](deploy/orgsyndb.env.example) lists the
settings:

| Setting | Default | Meaning |
|---|---|---|
| `ORGSYNDB_COLLECTION_REPO` | required | Git URL or path of the collection's repository |
| `ORGSYNDB_COLLECTION_REF` | `main` | Branch or tag to build |

| `ORGSYNDB_KEEP_RELEASES` | `2` | Published sites kept besides the current one |
| `ORGSYNDB_BUILD_TIMEOUT` | `3600` | Seconds the build and manifest commands may each take, at least 60 |
| `ORGSYNDB_REGISTRY_URL` | `http://app:8000/lab/registry/snapshot.json` | Registry snapshot fetched for each cycle |
| `ORGSYNDB_MANIFEST_URL` | `http://app:8000/lab/collection/manifest/` | App endpoint that receives each build's manifest |

and branch given by the `APP_REPO` and `APP_REF` build arguments, by default

### First account and tasks

To create the first administrator account, run this from `deploy/`:

```sh
docker compose exec app python manage.py createsuperuser
```

The command asks for a user name, email, initials and password. User names
follow Forgejo's rule: at most 40 characters, using ASCII letters and
digits with single `.`, `-` or `_` between them. A user name must start and
end with a letter or digit. Choose it before creating the account: it
cannot change later, and the admin shows it read-only.

Sign in at `/lab/admin/` to create further accounts. The admin requires staff
status. You can assign tasks to an account without a usable password
for a person who never signs in. Users change their own password through
their initials in the header, at `/lab/accounts/password/`. Procedure files
credit authors by user name. The site displays their account names; changing
a person's name changes the registry digest and triggers a site rebuild.

You cannot delete accounts in the admin, so their names stay on the task
history they wrote. To remove someone's access, deactivate their account
by clearing its **Active** flag in the admin.

Open `/lab/` for the [lab overview](#lab-overview). Choose **Aufgaben**
(**Tasks**) or open `/lab/tasks/` for the task list. Signing in still
leads to the task list. Reading needs no sign-in; every change requires
a signed-in account. The interface uses the latest accepted collection
import's German or English language, or German until an import is
accepted.

Each task has a number such as `T-001`, the substance it makes, priority,
assignee, start and end dates, ordered steps, calculated progress,
batch number, report and QC-list flags, and a note. QC means quality control;
the flag records whether the batch is on the QC list. Dates determine
whether a task is planned, running or ended; a task can also be
cancelled. Ended tasks missing the report or QC-list flag show
**Follow-up** and stay in the active list until both flags are set.

To enter a task, sign in and choose **New task**. In **Substance**, enter
a key from the [substance registry](#substance-registry); the suggestions
pair each key with its name. Add a missing substance in the registry
first. `/lab/tasks/new/?substance=cinnamic-acid`, for example, fills in
that key. Search the task list by substance key or either language's name.

In **Sequence**, choose an imported synthesis sequence by ID and title,
or leave it empty to plan steps yourself. You can choose any sequence
that is not withdrawn from the collection. Choosing one creates one task
step per sequence step, in the same order. Each step records the scope
entry it carries out and the import current when you planned it. A
**scope entry** is one combination of substrates and products in a
procedure. The task keeps its sequence, steps, entries and planned
imports if a later import changes or withdraws that sequence. You can
set, change or clear the task's sequence only while none of its steps
is done.

Without a sequence, **Steps total** sets the number of plain steps,
which have no scope entry or planned import. Increasing it adds steps
at the end; decreasing it removes the last ones. Leaving it empty
removes all steps. The total cannot fall below the number already done.
With a sequence, the form shows the task's step count and ignores changes
to **Steps total**. Clearing the sequence gives the task as many plain
steps as **Steps total** specifies.

**Steps done** marks the first that many steps done. Steps already done
keep their dates; newly done steps take today. The remaining steps have
their completion dates cleared. An empty value means none done, and the
value cannot exceed the number of steps. Progress counts done steps over
all steps, as a whole percentage rounded down. A task without steps has
no progress value.

Use **Beginnen** (**Start**) on the task page to start a planned task.
On a running task, **Stufe erledigt** (**Step done**) marks the first open
step done today. **Abschließen** (**End**) sets the end date to today and
marks every open step done on that date. On an ended task, the report
and QC-list buttons set those flags.

The task page links its sequence and lists steps in order. A step with a
scope entry links to its procedure by ID at `/procedures/<id>/`, with the
ID in lowercase. For a general procedure, **Eintrag &lt;n&gt;**
(**Entry &lt;n&gt;**) identifies the entry. A plain step appears as
**Stufe &lt;n&gt;** (**Step &lt;n&gt;**). A done step shows
**erledigt am &lt;date&gt;** (**done on &lt;date&gt;**).

A withdrawn sequence or procedure appears without a link, marked
**nicht in der Sammlung** (**not in the collection**). A step whose entry
was withdrawn also has no link. It shows the procedure ID and the entry's
signature, with that mark instead of an entry number. The signature has
the substrate keys, ` >> ` and the product keys; each side is sorted and
joined by ` + `. The task page's history combines task and step changes,
newest first. Step changes are headed **Stufe &lt;n&gt;** (**Step &lt;n&gt;**),
removals **Stufe &lt;n&gt; entfernt** (**Step &lt;n&gt; removed**).
Staff can also inspect a task's steps in `/lab/admin/`.

Planned and running tasks use a computed priority when their substance's
inventory article has a forecast. An article is one substance with its
article number and category, shared by all its container sizes. An article
without a number has no forecast, so its tasks keep their entered
priority. The computed priority is marked **berechnet**
(**computed**); hovering over it shows the task's slack in days, the time
left after allowing for delivery preparation and the remaining synthesis.
All other tasks keep the entered priority, marked **manuell** (**entered**).
The list, its ordering and its priority filter use this displayed priority.
You cannot override a computed priority; the form's priority applies while
no forecast computes one. See [Production planning](#production-planning)
for the calculation and its parameters.

The task page shows the matching article's runway (how many days the
stock lasts at the chosen certainty), synthesis time, slack and latest
start, with its article number linking to the planning list.
An article without consumption shows **Kein Verbrauch, keine Prognose.**
(**No consumption, no forecast.**). The same applies when all its items
are dormant or never delivered; see
[Stock levels](#enter-past-consumption-and-read-stock-levels).
A planned or running task also shows its own slack and is marked
**verspätet** (**late**) below zero. A running
task counts only its remaining synthesis time, so its priority can differ
from the article's priority for starting a new synthesis.

The task page links to bulk lots with the same nonempty batch when the
task and lot name the same substance. If you are signed in, an ended
task with a batch offers **Als Bulk erfassen** (**Record as bulk**).
This opens the new-lot form with the substance, batch and end date filled
in, including for a substance without an article.

### Lab overview

To check stock, decide what to synthesize next and see how much the lab
has delivered, open `/lab/`. **Labor auf einen Blick** (**Lab at a glance**)
is readable without signing in.

The stock bar under **Bestand** (**Inventory**) counts items at each
[stock level](#enter-past-consumption-and-read-stock-levels). Its segments
use the item list's colours and urgency order. Each segment's width shows
its share of the items, and its number is the item count at that level.
Hover over a segment for the level's name and count; choose it to open
the item list filtered to that level. Levels without items are absent.
The line below the bar gives the total number of items.

Four figures follow:

- **Abgegeben &lt;year&gt;** (**Delivered in &lt;year&gt;**) counts containers
  delivered from 1 January through today. **Vorjahr bis &lt;date&gt;: &lt;n&gt;**
  (**Last year to &lt;date&gt;: &lt;n&gt;**) compares the same span a year before.
  On 29 February, the comparison ends on 28 February of the previous year.
- **Fällige Synthesen** (**Syntheses due**) counts articles whose forecast
  priority is high or medium and links to planning. A badge
  **&lt;n&gt; verspätet** (**&lt;n&gt; late**) counts planned or running tasks
  with slack below zero.
  Slack is the runway left after the buffer for QC, filling and the
  unforeseen and after the synthesis time;
  [Production planning](#production-planning) explains the calculation.
- **Aufgaben** (**Tasks**) shows the running and planned task counts and
  links to the task list.
- **Offene Bulk-Lose** (**Open bulk lots**) counts lots of any substance with
  material remaining and links to the bulk list.

**Nächste Synthesen** (**Next syntheses**) lists up to five articles with
a forecast, smallest slack first, in the same order as planning's
**All articles** view. Each row shows the article number, name, priority,
latest start and a planned or running task when one exists. The article
number opens its first item in the item list's order. The task number
opens the task; its state and any **verspätet** (**late**) mark appear
beside it. Running tasks come before planned tasks, then task number
decides which one appears. **Zur Planung** (**To planning**) opens the
planning list. Without forecasts, **Keine Prognosen.** (**No forecasts.**)
replaces the table.

**Abgaben je Monat** (**Deliveries per month**) charts the twelve months
ending with the current month. Each month's bar sits beside a grey bar
for the same month a year before. Hover over a bar for its month, year
and container count.

**Meistgefragt &lt;year&gt;** (**Most requested in &lt;year&gt;**) lists up to
five articles with the most containers delivered this year, with names
and counts. **Empfänger &lt;year&gt;** (**Recipients in &lt;year&gt;**) lists
up to five recipients by the same measure; notes without a recipient
are excluded.
**Letzte Lieferscheine** (**Latest delivery notes**) shows the first five
notes in the delivery list, with number, date, recipient and container
count. Follow the number to open a note; a note without a number uses
`–` as its link. Empty lists show **Keine Abgaben.** (**No deliveries.**).

The yearly delivery figure, monthly chart and yearly lists use
delivery-note lines that count as consumption, using the note's date.
Reversed deliveries are excluded; notes entered later (**nachgetragen**)
count. Entered quarterly consumption is excluded because it has no day
or month. Years recorded only as quarterly values
therefore show no deliveries here. The comparison with last year becomes
meaningful once you have a year of delivery notes.

With `ORGSYNDB_LAB=true`, the site's home page embeds only the stock bar
and four figures from `/lab/summary/`, with a link to this overview. For
an existing container deployment, the next site build after pulling the
change adds that section. Follow
[Update the lab application](#update-the-lab-application) as well to serve
the summary; the builder updates only the static site.

### Substance registry

Before entering stock or planning a synthesis, find or add the substance
in the lab registry. A **substance** is a compound, mixture or solution
that you track as one material. Choose **Substanzen** (**Substances**) or
open `/lab/registry/`. You can read the registry without signing in;
creating or editing a record requires a signed-in account.

Search by key, English or German name, short name or CAS number, the
chemical registry identifier. The list shows substances in name order,
with their group, chemical classes, formula, molar mass and article number.
Open a substance's name to see its full record, containers, open bulk lots
and tasks. **In der Sammlung** (**In the collection**) links to the site's
compound page when the latest accepted import was received no earlier
than the substance was created. A substance added later gets the link
after a subsequent import is accepted. The app cannot tell whether the
site already serves that import's release. After a lost response to a
manifest, or for the demo data set's own import before the builder's
first build, the link can lead to a page the site does not serve yet.

#### Inspect collection imports

To check which collection build the app accepted, choose **Collection
imports** above the substance list or open `/lab/collection/`. You need
no sign-in. The page is headed **Imports**. It names the latest accepted
import's commit, release and received time, with counts of procedures
and sequences that are not withdrawn.

The table lists imports newest first. Its columns are **Received**,
**Commit**, **Trigger**, **Outcome**, **Release** and **Errors**. Commits
show their first ten characters. Triggers are **Commit**, **Registry**,
**Tooling** or **Catch-up**; outcomes are **Accepted** or **Refused**.
A refused import lists its errors, one per line. Before any import, the
page shows **No imports yet.**

Only an accepted import writes the collection's procedures, their authors,
scope entries and their substances, sequences and steps into the app's database. A
**scope entry** is one combination of substrates and products in a
procedure. The app matches it within its procedure by the sorted
substance keys on each side of `substrates >> products`. Changing yields
or order keeps the same entry; changing its substances creates a new
entry and withdraws the old one. A procedure or sequence absent from an
accepted import is marked withdrawn rather than deleted. Within an
imported procedure, an entry removed from its scope is also withdrawn.

The app keeps each procedure's authors as account rows, in file order.
An accepted import replaces that list when it differs from the manifest.

The app refuses an import when a procedure names an unknown substance or
reaction type, an author's user name has no account, two entries of one
procedure have the same substances, or an ID occurs twice. It also refuses
a sequence with an unknown target
substance or a step naming a procedure outside the collection or an entry
that procedure does not have. An unknown author reports
`<ID>: unknown author "<name>"`. A procedure must have at least one entry.
The refused import records every error and changes no procedure, entry
or sequence. Staff can inspect imports, procedures and sequences in
`/lab/admin/`, including each procedure's author rows; these records are
read-only, with no add, edit or delete actions.

#### Add substances and vocabulary terms

To add a substance, choose **Neue Substanz** (**New substance**). Enter
a key, such as `cinnamic-acid`, and an English name, choose a group and
check at least one chemical class. A key uses lowercase letters and
digits joined by single hyphens. It must be unique and cannot change
after creation. The key `group` is refused, since it names the directory
of the collection site's compound tabs. Use **Edit** on the substance's page to change its other
fields.

You can also enter a German name, short name, formula, molar mass in
g/mol, SMILES structure notation, CAS number and note. Formula, molar mass
and structure may stay empty, including for mixtures and solutions.
A molar mass must be above zero; you can enter a decimal comma. A CAS
number must have the correct form and check digit and must be unused.
A German interface shows the German name when present, otherwise the
English name.

The links above the substance list open four **vocabularies**, lists of
terms you can reuse: **Chemical classes**, **Groups**, **Projects** and
**Reaction types**. The first three allow a term to sit under a parent;
reaction types are a flat list. Each page shows keys, labels in both
languages, parents where applicable and how many substances use each
term. Parents appear before their children, with siblings ordered by key.

To add a missing group or class before creating a substance, open its
vocabulary and choose **New term**. Enter a unique key using the same
rule as substance keys and an English label. You can add a German label
and, in a tree, a parent. The parent cannot be the term itself or one
filed under it. Choose a term's key to edit its labels or parent; its
key stays fixed. Changes to substances and terms keep a history.
Staff can delete them in `/lab/admin/` only while no record uses them;
the registry pages offer no deletion.

#### Import a registry or copy its substance data

To load substance data from a collection in the old layout, use
`registry_import COLLECTION`. Its input must contain compound and
vocabulary files. The demo collection names a snapshot instead and is not
an input for this command. Both `registry_import` and `registry_load`
require an empty lab registry; run them before adding any substance or
vocabulary term.

The import reads `compounds/<key>.toml` and the vocabulary files
`chemical-classes.toml`, `inventory-groups.toml`, `projects.toml` and
`reaction-types.toml` under `vocabularies/`. It takes the compounds'
names, formula, molar mass, SMILES and CAS number, plus `short_name`,
`chemical_class`, `group` and `item_number`; the last becomes the article
number. Every compound must name a group and at least one chemical class.
Other fields, such as `structure_image`, `in_house` and `stock`, are left
out. One warning names these fields and counts the compounds that set
each.

To copy substance and vocabulary data from another lab, save
`/lab/registry/snapshot.json` from that server and load the saved file
with `registry_load FILE`. This JSON **snapshot** includes the four
vocabularies, substances and article numbers. Its `accounts` list contains
every account, active or not, ordered by user name, with `username` and
`name`, the account's display name. It also includes a format number, the
latest accepted collection import and a digest, a fingerprint of its
contents. The digest covers accounts, so changing a person's name triggers
a site rebuild; accepting an import does not change the digest.
`registry_load` ignores accounts and creates none. Create accounts in the
lab application's admin. Downloading the snapshot needs no sign-in.
Both commands load substance and vocabulary data in one transaction;
an unknown format, broken reference or invalid value leaves the registry
unchanged. Errors identify the record and field. The
[command reference](#lab-application-commands) gives local and container
invocations.

The site's compound pages, validator and Emacs read the registry named by
the collection, as described under [Compound registry](#compound-registry).
A rebuild accepted by the lab application publishes changes to substances
and terms on the static site; refresh the Emacs index to read those
changes in the editor. The lab application reads the collection's
procedures, their authors, scope entries, sequences and their steps from
accepted imports stored in its database. Tasks use these imported sequences and
scope entries. The latest accepted import supplies the interface language
and determines when substance pages link to the collection. Substance
names, molar masses and article numbers come directly from the lab registry.

### End-product inventory

Use the inventory to see which end products are ready to deliver and how
long their stock will last. The navigation lists **Bestand** (**Inventory**),
**Planung** (**Planning**), **Aufgaben** (**Tasks**), **Substanzen**
(**Substances**), **Verbindungen** (**Compounds**), **Synthesewege**
(**Sequences**), **Vorschriften** (**Procedures**) and **Hilfe** (**Help**)
in that order.
Choose **Bestand**, or open
`/lab/inventory/end-products/`. `/lab/inventory/` redirects to the same
list; `/lab/` opens the [lab overview](#lab-overview). You can read the
inventory without signing in. Use the same account as for tasks to enter
items, book stock changes or edit records.

The lists have three tabs: **Items**, **Bulk** at
`/lab/inventory/end-products/bulk/`, and **Deliveries** at
`/lab/inventory/deliveries/`. Bulk is material that has not yet been
divided into containers.

#### Enter items and find stock

An **article** is one substance with an article number and category;
the number may stay empty until its first delivery. An **item** is one
container size of that article. All sizes share the substance's name
and the article's number and category. Stock is a count of containers.

Choose **New item** on the item list. In **Substance**, enter a key from
the [substance registry](#substance-registry); suggestions show every
key with its name. Create a missing substance in the registry first.
Enter the container size and unit (`mg`, `µmol`, `g` or `mmol`), opening
count and note. No two items of one article may share size and unit,
even without an article number. The article, size and unit cannot change
after creation.

If the substance has no article, the form creates it with the optional
article number and category you enter. If it already has an article,
leave those fields empty to keep its values. A category you enter
replaces the category for every size. An article number you enter gives
the article one if it has none; otherwise it must match the existing
number. The number is unique among articles and is printed on delivery
notes.

To record where to find the containers in the freezer, enter **Fach**
(**Compartment**) and **Box** on **New item**. Both fields are optional
free text, at most 30 characters each. They suggest values already in
use, ordered with `2` before `10`, but you can enter another value.
Change them on **Edit** or in the admin when you move the containers.
The item page shows both locations, with `–` for each empty field.
The list shows them in the **Ort** (**Location**) popup and in the
optional **Fach** and **Box** columns.

Before the first delivery, choose **Enter article number** on the item
page to open **Edit**. The article-number field appears only while the
article has none. Enter the number once; it is fixed after you save it,
including in the admin, and appears on every size of that article.
You can still edit the category and the item's note. Clearing the category
on **Edit** clears it for every size. Change the name on the substance's
page, which the item links to; that page links to the collection's
compound when the latest accepted import was received no earlier than
the substance was created.

To set aside one container size, choose **Edit** on its item page and
change **Status** from **aktiv** (**active**), the default, to **nicht
benötigt** (**not needed**) or **auslaufend** (**discontinued**). You can
also change it in the admin. Either state makes that item dormant and
leaves it out of planning. The state applies to that size alone.
Discontinued items have no further restrictions on bookings or tasks.

For an item entered from paper records, give **Im Bestand seit** (**In
stock since**) the day it really entered the end-product stock. This
optional date is on **New item** and can be changed on **Edit**; it cannot
be after today. If it is empty, the first booking that leaves containers
sets it to the booking's date: an opening count above zero, a filling or
a correction. The item page shows the date.

An item whose stock entry date falls in the current calendar year carries
a blue superscript **neu** (**new**) beside its name in the item list and
on its page. The mark disappears on 1 January. Time spent as bulk does
not count towards this date.

An item without an article number shows its container and name; its page
heading is the name alone. It links to its substance and shows that
substance's open lots. Its article has no forecast; tasks of the same
substance keep their entered priority. You can fill containers from a
matching lot or without a lot and correct their count, but cannot book
deliveries or enter past consumption, even zero.
Its page offers **Enter article number** in place of **Book delivery**,
and has no **Enter consumption** or **New bulk lot** link.

Enter items and past quarterly consumption by hand; there is no Excel
import. The heading **Endprodukte** (**End products**) shows the number
of items in the whole inventory. To find stock, use the list's columns,
in order: **Artikelnr.** (**Article no.**), **Name**, **Kategorie**
(**Category**), **Gebinde** (**Container**), **Bestand** (**Stock**),
**Ø Jahr** (**Mean per year**), **Abgegeben** (**Delivered**),
**Reichweite** (**Coverage**), **Lagerort** (**Location**), **Fach**
(**Compartment**), **Box**, **Bulk verfügbar** (**Bulk available**) and
**Bemerkung** (**Note**). **Fach**, **Box** and **Bemerkung** start hidden;
show them with **Spalten** (**Columns**). **Bestand** counts containers,
**Ø Jahr** gives containers per year, and **Abgegeben** counts this year's
consumption in containers. **Reichweite** gives coverage in quarters.
Small lines under these headings show their units and the current year
for **Abgegeben**. Open an article number, or the name of an item without
one, to see its item page.

To find the material without leaving the list, choose **Ort** in
**Lagerort**. Under **Fertige Gebinde** (**Finished containers**), the
popup shows the compartment and box, with **nicht hinterlegt** (**not
recorded**) for an empty field. Under **Bulk, separat gelagert** (**Bulk,
stored separately**), it lists each open bulk lot of the article with
its location, batch and amount. An unrecorded bulk location also reads
**nicht hinterlegt**. Open a batch to see its lot page, or choose
**Artikel und Lagerort öffnen** (**Open item and location**) for the item
page.

To read consumption in more detail, choose the number in **Abgegeben**.
The popup shows this year's consumption up to today and the means per
year and quarter. A mean projected from the current year is italic;
`–` means there is no mean. A bar chart shows the current year's quarters,
marking the current quarter **laufend** (**running**). A table shows each
quarter and the year's total for the two previous years and the current
year. Future quarters have no bar and stay empty in the table. The popup
names the years with consumption entered by hand and warns that the
current year is incomplete. Choose **Alle Quartale und Buchungen öffnen**
(**Open all quarters and movements**) for the item page, where you can
also read the quarterly mean.

Both popups identify the item by its name, article number when present,
container size and stock count. They open beside their buttons and
highlight the row. Press Escape, click outside or use the close button
to close a popup.

The **Bestand** column shows container counts alone, coloured by stock
level. Hover over a count to read the level's name; screen readers also
read it. Open **Bestandsstatus** (**Stock status**) above the table for
all seven colours, their names and meanings in urgency order. Each entry
counts the items matching your search, category and other filters, so
its count tells you how many items choosing it lists. Choose a level to
list exactly those items, keeping the other filters and order. Choose
**Alle Bestandsstatus** (**All stock statuses**) to include every level.
The button shows the chosen level, or **Alle** (**All**), and its count.

To narrow the list, use the filters above the table. **Artikel suchen**
(**Search items**) finds text anywhere in the article number, category,
note or the substance's key, English or German name and short name,
regardless of case. Press Enter to search. **Kategorie** offers
**Alle Kategorien** (**All categories**) or
one category in use. Open **Weitere Filter** (**More filters**) for
**Gebinde**, **Fach** and **Box**. Each offers **Alle** or one value in use;
choose a value to match it exactly. Container choices show size and unit;
locations are ordered with `2` before `10`. **Weitere Filter** shows how
many of its three filters are in force. Choices apply as soon as they
change, and the controls show the filters in force. Consumption,
coverage and bulk have no filter.

The line above the table shows how many items match out of the whole
inventory and names the order in force. While any filter is in force,
**Zurücksetzen** (**Reset**) at the end of that line clears every filter
and keeps your order.

To reorder the list, choose any column header except **Lagerort**.
Choose it again to reverse the order; ▲ or ▼ marks the sorted column.
Sorting keeps your filters, and filtering keeps your order. You can
bookmark the filters and order. Text sorts regardless of case. Containers
sort from smallest to largest, with mass sizes before amount-of-substance
sizes: 100 mg, 250 mg, 1 g, then µmol sizes. Locations sort with `2` before
`10`. Consumption and coverage sort by value, smallest first; bulk sorts
by how many containers the open lots would fill. Items without a value
in the sorting column come last in either direction. Ties sort by article
number, then container size. Unnumbered items follow numbered ones and
sort by name, then container size.

To put urgent items first, sort by **Bestand** in ascending order (▲).
This orders items as out, critical, low, watch, sufficient, never delivered
and dormant, with the shortest coverage first within each level. Items
without coverage come last within their level in this order.

The default order is by category, then article number, then container
size in the order described above. Items without a category come last.
Within a category, items without an article number follow those with one,
ordered by name, then container size. A darker line separates categories
when you sort by **Kategorie**. Each size has its own row showing its
name and article number when present, in every order. Each numbered row
keeps its own article-number link and, when you are signed in, its own
check box.

To spot heavily used items, compare the five colour steps in **Ø Jahr**
and **Abgegeben**. Each column ranks its positive values across the whole
inventory into fifths, from least to most consumed; equal values share a
step. The scale compares all categories and container sizes together.
Zero and missing values stay uncoloured, and filtering does not change
the colours. Above the table, **Verbrauch einfärben** (**Colour
consumption**) shows the scale from **wenig** (**little**) to **viel**
(**much**). It is checked by default; uncheck it to hide the consumption
colours.

To fit more information on screen, use **Spalten** to show or hide any
column except **Artikelnr.**, **Name** and **Bestand**. **Zeilenhöhe**
(**Row height**) offers **Kompakt** (**Compact**), the default, and
**Sehr kompakt** (**Very compact**). Your browser remembers the columns,
row height and consumption-colour choice across pages. These choices
are separate from the filters and order saved in a bookmark.

The list uses one small script to place popups, apply filter choices and
remember view controls. Without JavaScript, popups open in the centre of
the window, and **Filtern** (**Filter**) applies the filters. The view
controls still work, but their choices last only until you leave the page.

For a long or wide list, scroll inside the table's box. The column headers
stay at the top, and **Artikelnr.** stays at the left. The box is at most
the window's height. Printing shows the whole table with your chosen
columns, without filters, menus, view controls, the note below the table
or the **Lagerort** column. Show **Fach** and **Box** before printing to
include the locations.

#### Book deliveries and correct counts

Enter the item's article number before its first delivery. Delivery-note
rows offer only items with an article number, for current and historical
deliveries alike. A delivery note (`Lieferschein`) holds an optional
number, date, recipient, note and up to ten lines of items and container
counts.

To book a request for several articles, sign in and tick their rows in
the item list's **Artikelnr.** (**Article no.**) column. Only items with an
article number have a check box. Choose **Lieferschein mit Auswahl**
(**Delivery note from selection**) above the table. The new note form
opens with the selected items in its first rows, in the list's order
from top to bottom. Enter the container counts. If you select more than
ten items, only the first ten appear; book a second note for the rest.

For one item, choose **Book delivery** on its item page to fill the
note's first row. To start an empty note, choose **New delivery note** on
the deliveries list. Each item choice shows the article number,
container size, name and location, for example
`CH-0012 · 100 mg · (E)-Zimtsäure · Fach 2 / Box 7`.
An empty compartment or box is left out of the label; an item with neither
shows no location.

Booking the note reduces stock for all lines together. If any line
exceeds the available stock, the whole note is refused and nothing
changes. The deliveries list shows newest notes first and lets you
filter by text or item.

The note's page shows **Fach** and **Box** beside every line. Print it to
use as a pick list when fetching the containers. These are the items'
current locations: historical notes and reprints also show where the
items are now.

Stock changes only through bookings: the opening count, deliveries,
fillings, corrections after counting, and reversals. The item page keeps
these in a ledger showing the date, person and count after each booking.
Choose **Correct count** after counting the containers, and give a note
explaining the correction. To undo a mistaken delivery or filling,
choose **Reverse** beside its ledger entry and give a note. A reversed
delivery restores stock and no longer counts as consumption. Reversing
a filling removes its containers and returns any amount taken to its
bulk lot; it is refused if those containers are no longer available.

You cannot edit or delete ledger entries or delete delivery notes. A
delivery note's date and lines are fixed; its number, recipient and note
can be edited. Reverse a current note's deliveries one line at a time
from the items' ledgers.

#### Enter past consumption and read stock levels

On an item page with an article number, choose **Verbrauch nachtragen**
(**Enter consumption**) to enter a past or current quarter's container
count. You cannot enter a quarter that has not begun.
Entering another value for the same quarter replaces it; leaving the
count empty removes it.
Subsequent deliveries add to consumption in the quarter of the delivery
note's date.

To record old paper delivery notes, tick **nachgetragen – Bestand bleibt
unverändert** (**entered later – stock unchanged**) on the delivery form.
These notes add consumption without changing stock. For each item and
quarter, use either an entered consumption value or these old notes;
the application refuses to combine them. Remove an entered value before
entering the old notes behind it. You can reverse a note entered later
as a whole, with a required note explaining why.

The yearly mean normally covers complete calendar years before the
current year, starting with the item's first year with data. The quarterly
mean is a quarter of that yearly mean. The current year has its own column
and normally does not enter the mean.

If all consumption above zero falls in the current year, the application
projects the means from that year instead. It counts the days from the
start of the quarter with the first positive consumption through today,
including today, using at least 91.3125 days, one average quarter. The
projected quarterly mean is this year's consumption times 91.3125 divided
by that day count; the yearly mean is four times the quarterly mean.
From the next year, the means use complete calendar years again.

**Coverage** is stock divided by the quarterly mean, expressed in
quarters. It is blank without a positive mean and for dormant or
never-delivered items; their means still show when available. Projected
means and the coverage calculated from them appear in italics in the
list and on the item page. Hover over them to see **hochgerechnet aus
dem laufenden Jahr** (**projected from the current year**). These means
also determine the stock level. The item page shows quarterly consumption
for the last two complete years and the current year as a bar chart and
table.

Every item has exactly one stock level: the first matching row below.
The item page and planning list show the level's name alongside its
coloured stock count; the item list shows the count alone.

| Level | Colour | When it applies |
|---|---|---|
| ruhend (Dormant) | Dark grey | Set aside as not needed or discontinued, or has positive consumption but none in this calendar year or the previous one |
| noch nie abgegeben (Never delivered) | Light slate blue | No consumption above zero |
| aufgebraucht (Out) | Red | No containers |
| kritisch (Critical) | Orange | Above zero, below half the quarterly mean |
| niedrig (Low) | Yellow | At least half the quarterly mean, below the quarterly mean |
| beobachten (Watch) | Pale green | At least the quarterly mean, below twice that mean |
| ausreichend (Sufficient) | Darker green | At least twice the quarterly mean |

Dormant and never-delivered items keep those levels even with no
containers left. A positive entered consumption value counts when
deciding whether an item has been delivered, as do delivery notes.

The item page's **Prognose** (**Forecast**) section shows how demand is
estimated and how many days the filled containers last at the chosen
certainty, its runway on hand. It also shows the article's usable bulk,
combined runway for all sizes, synthesis time with its basis, slack,
latest start and priority. Figures estimated from quarterly totals are
marked **grob** (**rough**). A dormant item shows **Ruhend, keine
Prognose.** (**Dormant, no forecast.**). Without consumption, it shows
**Kein Verbrauch, keine Prognose.** (**No consumption, no forecast.**).

The forecast gives the amount a new synthesis must yield to cover its
synthesis time, the delivery buffer and the target coverage, beyond the
containers and usable bulk already available. It also shows the last
delivery and the number of deliveries in the past 365 days. With at least
three delivery notes in the past 730 days, it shows their usual interval,
the median gap in whole days, and the next delivery expected that long
after the last. Each forecast figure names the parameters it uses.

#### Record bulk and fill containers

Choose **New bulk lot** on the bulk list to record material not yet
divided into containers. Choose any substance by key, including an
intermediate or a reagent made in the lab. Choose **hergestellt** (**made**),
the default, or **gekauft** (**bought**), and optionally enter a supplier.
The same substance can have made and bought lots. Enter the amount in
`mg`, `g`, `µmol` or `mmol`, batch, location, date and note. The substance,
source and unit cannot change after creation.

The bulk list shows all open lots, including substances without an
article. It shows the substance's name, article number when present and
source, with the supplier beside it when given. Each lot's page has its
own ledger; correcting its amount requires a note. A lot at zero is used
up and leaves the bulk list unless you tick **Used-up lots too**.

The lot page links to tasks with the same nonempty batch and substance.
The new-lot form at `/lab/inventory/bulk/new/` accepts `substance`, `batch`
and `made_on` in the query to fill in the substance key, batch and date.
The task page's **Record as bulk** link supplies these values from the
ended task.

On an item page, choose **Fill** to add containers. You may select an
open bulk lot of the same substance and enter the amount taken in the
lot's unit. **Menge vorschlagen** (**Propose amount**) calculates the
amount for the container count without booking it. Leaving the amount
empty when booking uses that proposal. Conversion between mass and
amount of substance uses the molar mass in the registry; without it,
enter the amount yourself. Booking adds the containers and deducts the bulk
amount together. If the lot has too little material, neither changes.
Each item shows its open lots and how many containers they could still
fill, counted separately for each lot.

Staff can inspect articles, items, bulk lots, delivery notes and movements
at `/lab/admin/`. An item or lot can be deleted only while its ledger holds
just its opening entry; an item must also have no delivery-note lines.
Deleting such an item or lot also deletes its opening entry.
An article can be deleted only while it has no items; its article number
is read-only once set.

The inventory needs no new settings or services. Follow
[Update the lab application](#update-the-lab-application) to deploy it;
the `app` container applies the inventory migration on startup.

### Production planning

Use production planning to decide when to fill containers or start a
synthesis. It computes a priority from consumption, available stock and
synthesis durations, with the same figures visible to everyone. Choose
**Planung** (**Planning**) or open `/lab/planning/`.

Planning groups the container sizes of an article because one synthesis
replenishes the bulk used to fill them. Tasks and bulk lots match the
article by substance. An article without a number has no forecast.
Dormant and never-delivered items have no demand model, runway or actions
and do not contribute to planning figures. If every item is dormant or
never delivered, the article has no
forecast. These sizes still appear with their stock levels when another
size gives the article a forecast.

An article's **runway** is how many days the stock lasts at the chosen
certainty, 95 % by default. Bulk is shared between sizes so that it counts
once. **Usable bulk** counts each convertible open lot's amount less the
largest container size with demand, at least zero, so that the amount
counted can fill whole containers.

The synthesis time is the longest of the article's last three completed
syntheses; cancelled tasks do not count. Until three exist, the default
of 21 days also counts. **Slack** is runway minus the buffer for QC,
filling and the unforeseen, minus synthesis time. **Latest start** is
today plus that slack. By default, priority is high below 14 days of
slack, medium from 14 to below 56, and low from 56. Work already under way
does not change the article's priority.

With enough delivery-note orders, the forecast uses their measured rate
and sizes. Otherwise it estimates demand from quarterly totals and marks
its figures **grob** (**rough**). Forecasts depend on the entered history;
they assume independent orders at a steady rate and do not model seasons.

The planning list shows articles with a forecast whose priority is high
or medium, or for which an action is due. Choose **All articles**
(`/lab/planning/?all=1`) to see every article with a forecast. Rows are
ordered by slack, smallest first, then by article number. Each row shows
the article number and name; each container size with stock, level and
runway on hand; demand per year; last delivery; usable bulk; article
runway; synthesis time; latest start; priority; tasks; and actions.
Container sizes link to their item pages. Planned and running tasks link
to their task pages and show their expected end, with **verspätet**
(**late**) when their slack is below zero. The line above the table shows
the parameters in force.

Use the actions offered for each article:

- `Abfüllen <size>` (`Fill <size>`) opens that size's filling form
  when its filled containers last less than the buffer and the open lots
  can fill at least one container.
- **Bulk prüfen** (**Check bulk**) opens the bulk list when an open lot
  cannot be converted because its substance has no molar mass in the
  registry.
- **Synthese planen** (**Plan synthesis**) opens a new task with the
  substance key filled in. It appears when priority is high or medium,
  no matching task is planned or running, and every open lot converts.
  An unconvertible lot may hold enough material, so check it first. This
  action is a link when you are signed in and plain text otherwise.

Staff edit one parameter record at `/lab/admin/planning/parameters/`;
changes stay in its history. The defaults apply when no record exists.

| Parameter | Default | Range and meaning |
|---|---|---|
| Certainty | `0.95` (95 %) | `0.5`–`0.999`; probability that stock lasts its runway |
| Buffer | 28 days | 0–365 days; time from synthesis end until the product can be delivered, for QC, filling and the unforeseen |
| Default synthesis time | 21 days | 1–730 days; also counts until three completed syntheses exist |
| History | 12 quarters | 4–40 complete quarters for estimating demand |
| Minimum orders | 6 | 3–100 orders; below this count, quarterly totals give a rough forecast |
| High priority below | 14 days of slack | At least 0 and below the medium threshold |
| Medium priority below | 56 days of slack | Above the high threshold |
| Target coverage | 365 days | 30–1095 days beyond synthesis time and the buffer for sizing a new synthesis |

Production planning needs no new settings or services. Follow
[Update the lab application](#update-the-lab-application) to deploy it;
the `app` container applies the `planning` migration on startup.

### Repository access

For an `ssh://` repository, put the private key, a `known_hosts` file
holding the server's host key, and optionally an SSH `config` into a
directory, make the key owned by UID 1000 with mode 600, and enable the
commented `./ssh:/home/orgsyndb/.ssh:ro` mount in `compose.yaml`. The
`builder`, `web` and `app` containers run as user `orgsyndb` with UID 1000.
An `https://` repository that needs a password can carry a read-only access
token in its URL.

For a repository on the server itself, mount it under `/srv/git/` and name
it by that path:

```yaml
    volumes:
      - data:/var/lib/orgsyndb
      - /home/me/procedures:/srv/git/procedures:ro
```

```sh
ORGSYNDB_COLLECTION_REPO=/srv/git/procedures
```

The repository's files must be readable by UID 1000. Git trusts
repositories under `/srv/git/` although another user owns them. Only
committed changes on the named branch are built, never the working tree.

### Builds and updates

`deploy/compose.yaml` sets `ORGSYNDB_LAB=true` for `builder`, so the site
it builds links the lab application's views first. This setting belongs
to the Compose file; it is not set in `orgsyndb.env`.

Each cycle fetches the application's branch, if updates are on, and the
collection's branch. It also requests the lab application's registry
snapshot at `ORGSYNDB_REGISTRY_URL`, which defaults to
`http://app:8000/lab/registry/snapshot.json`, with a 30-second timeout.
The request's `Host` header is the first entry of `ORGSYNDB_ALLOWED_HOSTS`
that is not `*`, with a leading `.` removed, or `localhost` if there is no
such entry. The builder and app share `orgsyndb.env`, so the request needs
no separate host setting.

The builder writes the fetched snapshot to `<data>/registry.json`;
`<data>` is the data volume's directory, `/var/lib/orgsyndb` by default.
If the request fails or returns something other than a snapshot, the
cycle builds nothing. Only the app can accept a build, and the builder
needs its current snapshot to know what it last accepted. The log says:

```text
cannot fetch the registry from <url>: <reason>; nothing is built
```

The snapshot names the latest accepted import. Before deciding whether to
build, the builder points `<data>/current` at that import's release when
the release exists in `<data>/releases/`. This also restores an accepted
release after a lost response to its manifest. Without
`ORGSYNDB_BUILDER_TOKEN`, the builder still restores that release but
builds nothing. Its log begins `ORGSYNDB_BUILDER_TOKEN is not set`.

A build is needed when the collection commit, registry digest or
application commit differs from the latest accepted import's, or that
import's release is missing. The digest is a fingerprint of the registry's
contents, including accounts and their names. Changing a person's name
therefore triggers a rebuild. Accepting an import does not change the
digest. The manifest records the first matching trigger in this order:

| Trigger | When it applies |
|---|---|
| `commit` | The collection commit differs |
| `registry` | The registry digest differs |
| `tooling` | The application commit differs |
| `catch-up` | No import has been accepted, or its release is missing and all three values match |

For a combination of application commit, collection commit and registry
digest that needs building and has not been recorded as failed, the
builder checks out both commits. It runs `orgsyndb build`, or
`orgsyndb pdf` with `ORGSYNDB_PDF=true`, followed by `orgsyndb manifest`.
`ORGSYNDB_BUILD_TIMEOUT` applies separately to each command. Every
invocation receives `ORGSYNDB_REGISTRY` naming
`<data>/registry.json`, so the site and manifest describe the same
registry snapshot. A command that fails or exceeds its timeout counts as
a failed build.

The builder stages a successful build in
`<data>/releases/<serial>-<app>-<commit>`, containing `public/` and, when
PDFs are enabled, `pdf/`. The serial starts at `000001`; both commits use
their first ten characters.
Staging leaves the served site in place.

The builder then posts the manifest to `ORGSYNDB_MANIFEST_URL`, with
`Authorization: Bearer <token>` using `ORGSYNDB_BUILDER_TOKEN`, the
snapshot request's `Host`, and a 30-second timeout. The manifest describes
the collection's language, procedures with their author user names in file
order, scope entries, sequences and steps. It also identifies the build,
commits, registry digest, latest
accepted import used as its base, trigger and staged release. The app
accepts a build only while that base is still the latest accepted import
and the registry digest is still current, and after checking the
collection's references.

| App response | What the builder does |
|---|---|
| `accepted` | Publishes the release by atomically pointing `current` at it, records it as deployed, and keeps the current release plus the `ORGSYNDB_KEEP_RELEASES` newest others |
| `refused` | Removes the staged release, leaves the served site in place, and records the combination as failed |
| `stale` | Removes the staged release and records no failure; the next cycle builds again with a fresh snapshot |
| No response or another response | Logs `cannot send the manifest: <reason>`, keeps the staged release and records no failure; a later cycle publishes it if the snapshot names it as accepted, otherwise it builds again |

These log lines identify publication, restoration, refusal and staleness;
the timestamp and `orgsyndb-deploy:` prefix are omitted here:

```text
published release <name>
published release <name>, which the application accepted
the application refused release <name>; the published site is unchanged
the application found release <name> stale; the next cycle builds again
```

A failed build leaves the served site in place. Its output stays in the
`builder` log, and the builder reports it to the app as `refused`. The
report contains output lines with `: error: `, or the failure message
when there are none. The builder records the combination as failed only
once the app answers the report. If it cannot send the report, it logs
`cannot send the manifest: <reason>`; the next cycle builds again and
reports the failure then. Accepted and refused imports appear on the
[imports page](#inspect-collection-imports).

A new application commit is tried first with the newest collection
commit. Once a failure or refusal is recorded for that build, the
builder tries the previous application commit with the same collection
commit and snapshot. A combination recorded as failed is
skipped on later cycles; the builder keeps up to 50 failed combinations.
A new commit of either repository or a changed registry digest creates
another combination to try. If the collection cannot be fetched, the
builder uses its last fetched commit when one exists. If the application
cannot be fetched, it stays on its current commit.

The image holds the build tools and the update program. An application
commit that changes `deploy/docker/` needs a new image, so `builder` logs
that and stays on its current application commit. Rebuild the image then:

```sh
docker compose build --pull && docker compose up -d
```

Recreating the `builder` container returns the application to the commit
the image holds; the next cycle updates it again.

To start a cycle at once instead of waiting, and to see what is
published:

```sh
docker compose kill -s HUP builder
docker compose exec builder orgsyndb-deploy status
```

`status` prints the application and collection commits of the published
site, its registry digest under `deployed.registry`, and the combinations
that failed. After a failure unrelated to the recorded combination, such
as a network outage while fetching a tool,
`orgsyndb-deploy retry` forgets the failed combinations so that the next
cycle builds them again.

With `ORGSYNDB_APP_UPDATE=true`, every commit on the followed application
branch reaches the site's builder within one interval. The default,
`main`, moves only to tested commits of `develop`. Following `develop`
brings the newest work, untested on the server, so use it only for a
trial server.

### Update the lab application

Update the lab application deliberately so you can back up its records
before applying database changes. The builder's automatic updates apply
to the static site only. From `deploy/`, pull the new code, take a backup,
and rebuild `app`:

```sh
git pull
docker compose run --rm backup once
docker compose up -d --build app
```

Continue with the rebuild only if the backup succeeds. On startup,
`app` applies pending migrations, the changes to the database's tables,
before serving requests.

### Back up and restore lab records

The `backup` service writes a database dump every 24 hours and keeps the
14 newest dumps. Change `ORGSYNDB_BACKUP_HOURS` and
`ORGSYNDB_KEEP_BACKUPS` to adjust this. Each file is named
`lab-<UTC time>.dump`, with time written as `YYYYMMDDTHHMMSSZ`, under
`deploy/backups/`. It uses `pg_dump`'s custom format, read by
`pg_restore`. Files have mode 600 and belong to root, so copying them
elsewhere requires root access.

To take a backup immediately, run this from `deploy/`:

```sh
docker compose run --rm backup once
```

To restore a dump, stop `app`, restore the database, and start `app`
again. From `deploy/`, replace the file name below with the dump you
want to restore. `sudo cat` reads the root-owned file; the database
container supplies `POSTGRES_USER` and `POSTGRES_DB` from `orgsyndb.env`:

```sh
docker compose stop app
sudo cat 'backups/lab-<UTC time>.dump' | docker compose exec -T db sh -c \
  'pg_restore --clean --if-exists -U "$POSTGRES_USER" -d "$POSTGRES_DB"'
docker compose start app
```

### HTTPS

The default Caddyfile, `deploy/docker/Caddyfile`, serves plain HTTP. For
HTTPS, mount a Caddyfile of your own over `/etc/caddy/Caddyfile` in the
`web` service, using `/var/lib/orgsyndb/current/public` as its root and
preserving the `/lab/` forwarding to `app`, or put the server behind the
organisation's reverse proxy.

## Serve a copy with Caddy

`orgsyndb build` creates the deployable site in the collection's `public/`.
Without containers, [deploy/Caddyfile.example](deploy/Caddyfile.example)
shows how Caddy can serve a copy of that directory. Replace
`orgsyndb.internal` with the server's internal host name and
`/srv/orgsyndb/public` with the directory containing the copied site. Review
the example's `tls internal` setting against your organisation's TLS setup.

This repository publishes only its demo collection to GitHub Pages with
[`.github/workflows/demo-site.yml`](.github/workflows/demo-site.yml). The
workflow builds `examples/demo/` in a `fedora:44` container with
`tools/orgsyndb -C examples/demo build`, then uploads
`examples/demo/public`. A push to `main` builds and deploys the site. A push
to `develop` or a pull request builds it without deploying. You can also
start the workflow by hand. Deployment runs only for `main`.

To publish the demo from a fork, set the repository's Pages source to
**GitHub Actions** under **Settings > Pages**. The workflow needs no
repository secrets. The demo works below a path such as `/orgsyndb/`
without additional configuration: Hugo writes relative URLs, and Pagefind
finds its files and result links from the location of its own script.
