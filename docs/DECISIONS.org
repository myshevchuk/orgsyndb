* Governance and formats

** Stage the work as schema, pipeline, then theme

- Decided :: Use three OpenSpec changes, each on its own branch and merged
  with a merge commit after archive: schema, build pipeline, then theme.
- Why :: The theme needs exported Org content, so the pipeline must exist
  before the site can render all samples.
- Rejected :: The brief's pipeline-after-site order was rejected because Org
  samples could not render before export existed.

** Check proposals before implementation

- Decided :: Give every proposal a separate design check before
  implementation; the owner chose not to run the final implementation-review
  gate; the result was verified separately.
- Why :: Early checks catch interface and acceptance problems while the
  design can still change cheaply.
- Rejected :: Running both formal gates was not selected for this project.

** Match document format to the reader

- Decided :: Keep the repository front page, schema, and co-worker guide in
  Markdown; keep the owner's Org authoring guide and this record in Org.
- Why :: The co-worker reads outside Emacs, while the owner uses Org for
  owner-only documents.
- Rejected :: The brief's Markdown names for the owner-only authoring and
  decision documents were replaced.

** Keep the repository safe to publish

- Decided :: Treat the project as a public GitHub repository and keep user,
  machine, and deployment identifiers out of committed files.
- Why :: The owner requested a public repository, and its files must work on
  another machine.
- Rejected :: Committing deployment-specific, user-specific, or
  machine-specific identifiers was rejected.

** Target verified tool versions

- Decided :: Target Hugo 0.162.1, WeasyPrint 70.0, Emacs 30.2 with Org
  9.7.11, ox-hugo 20251206.1738, tomelr 0.4.3, Pagefind 1.5.2, and Python
  3.14 standard-library code.
- Why :: These are the Fedora tool versions against which behavior and
  compatibility were checked; the Hugo implementation uses only standard
  build features.
- Rejected :: Floating upstream versions and dependencies that require Node
  for normal builds were rejected as unreproducible or unnecessary.

* Schema

** Use one schema and validator for both source formats

- Decided :: Validate exported Org procedures and hand-written Markdown
  procedures through one standard-library Python validator with explicit
  content roots.
- Why :: One validation path keeps the two authoring formats equivalent and
  produces actionable messages for an author who does not know Hugo or TOML.
- Rejected :: Separate validators, working-directory defaults, a config file,
  and JSON-only output were rejected as duplication or hidden behavior.

** Lint Org sources and cross-check their exports

- Decided :: Check the required Org keywords in the source and compare its
  timestamps and model field with the matching exported Markdown file.
- Why :: Exported TOML alone cannot prove that the Org-only keywords were
  present and correctly formed.
- Rejected :: Putting the lint in Emacs Lisp or exporting extra raw keywords
  was rejected because either splits the rules or pollutes published data.

** Derive every procedure URL from a required slug

- Decided :: Require ~slug~ to equal the lowercase procedure ID and publish
  the page at ~/procedures/:slug/~.
- Why :: Hugo has no permalink token for an arbitrary ~id~ field, while
  ~slug~ gives a stable URL that the validator can check exactly.
- Rejected :: Per-file ~url~ fields, build-time file renaming, content
  adapters, and case-tolerant slugs added more ways for the ID and URL to
  drift.

** Use Berlin wall time and explicit offsets

- Decided :: Org stores Europe/Berlin local wall-clock timestamps; exported
  TOML stores offset datetimes, and ~lastmod~ is compared with ~date~ as an
  instant.
- Why :: The project records Berlin wall time, including CET/CEST clock
  changes, while the exported value must identify an unambiguous instant.
- Rejected :: Fixed GMT+1 is wrong for half the year. Strings, local TOML
  datetimes, and rejecting every repeated-hour timestamp were also rejected.

** Treat unknown metadata as a warning

- Decided :: Validate known schema fields, tolerate a small typed set of
  Hugo fields, reject ~draft = true~, ~author~, and ~url~, and warn on other
  unknown keys.
- Why :: Warnings catch misspelled optional fields without making the build
  brittle when an exporter adds harmless metadata.
- Rejected :: Rejecting every unknown key and silently accepting every key
  were both rejected.

** Fix the eight body sections but warn on mistakes

- Decided :: Recognize the eight canonical Markdown level-two headings in
  order, with Org top-level headings exporting to them, and report missing or
  reordered sections as warnings.
- Why :: Template-shaped, case-insensitive heading checks give useful
  guidance without making incomplete prose invalid.
- Rejected :: Fuzzy matching, a Markdown parsing dependency, case-sensitive
  matching, and errors for missing sections were rejected.

** Store reaction types as labelled vocabulary entries

- Decided :: Put one TOML table per reaction-type slug in
  ~site/data/reaction_types.toml~, with a human-readable ~label~.
- Why :: The validator gets controlled values and the site gets correct
  display names without guessing how to title-case a slug.
- Rejected :: A flat list, an array of tables, and mechanism-level categories
  were rejected as awkward to look up or too fine-grained.

** Keep templates valid and visibly unfinished

- Decided :: Use the invalid placeholder ID ~OSDB-0000~, a matching lowercase
  slug, and the ordinary tag ~change-me~ in templates.
- Why :: The templates remain parseable and testable, while an unfilled copy
  fails validation and a new real procedure is not marked as sample data.
- Rejected :: Non-parseable template tokens and a default ~sample-data~ tag
  were rejected.

** Repeat Org custom-front-matter keywords and put product last

- Decided :: Repeat file-level ~#+HUGO_CUSTOM_FRONT_MATTER~ lines and keep
  the map-valued ~:product~ line last.
- Why :: The documented plus-suffix continuation applies to property
  drawers, not file-level keywords, and tomelr otherwise places later keys
  inside the product table.
- Rejected :: Plus-suffix file keywords and metadata after ~:product~ were
  rejected because they do not export with the intended TOML structure.

** Keep procedure directories flat and diagnostics focused

- Decided :: Examine only top-level procedure files, reject subdirectories,
  and suppress checks that depend on a missing or malformed value.
- Why :: The content mounts are flat, and one primary mistake should not
  produce a cascade of secondary messages.
- Rejected :: Recursive discovery and continuing every dependent check were
  rejected as incompatible with the site layout or confusing to authors.

* Export and build

** Put policy in Python behind a fish entry point

- Decided :: Use ~tools/build.fish~ as the user interface, a standard-library
  Python core for testable pipeline decisions, and thin Emacs Lisp for Org
  export.
- Why :: Timestamp arithmetic, template filling, recovery, hashes, and PDF
  job selection can be unit-tested without exercising every external tool.
- Rejected :: All-fish logic, timestamp policy in Emacs Lisp, and a separate
  PDF script were rejected as harder to test or duplicative.

** Pin and isolate the Org export packages

- Decided :: Install ox-hugo and tomelr from exact Git commits into
  ~.emacs-batch/~ and verify their checkouts on every export.
- Why :: A fresh clone then uses the versions that were tested without
  reading or writing the owner's Emacs configuration.
- Rejected :: Latest package archives, MELPA Stable, vendored package trees,
  and generated GitHub archives were rejected as moving, bulky, or not
  guaranteed byte-stable.

** Parse Org timestamps before export

- Decided :: Parse ~#+CREATED~ and ~#+LAST_MODIFIED~ in the pipeline and
  inject RFC 3339 values into a temporary export buffer.
- Why :: Org's timestamp parser drops seconds, and the pipeline must preserve
  both seconds and the correct Berlin offset, including the repeated hour.
- Rejected :: Trusting Org's parsed value, always choosing one side of the
  repeated hour, and running one Emacs process per file were rejected.

** Make exports deterministic and recoverable

- Decided :: Re-export every Org source into a staging directory, seed Org
  reference IDs per file, and replace the live export with same-directory
  renames and crash recovery.
- Why :: Unchanged inputs produce byte-identical Markdown, orphaned exports
  disappear, and an interrupted build leaves a complete old or new export.
- Rejected :: In-place and mtime-based incremental export, delete-then-rename,
  symlink swaps, and output inside committed content were rejected.

** Keep Emacs export state inside the repository

- Decided :: Redirect the Emacs user directory, package data, Org persistence,
  native compilation state, and temporary export files into generated
  repository directories.
- Why :: Batch export must not depend on or modify ~$HOME~ or the inherited
  temporary directory.
- Rejected :: Loading the owner's Emacs setup or allowing transient state in
  per-user locations was rejected.

** Mount both validated content trees and publish every valid date

- Decided :: Mount ~build/export/~ and ~md/procedures/~ into the Hugo
  procedures section, and enable ~buildFuture~ and ~buildExpired~.
- Why :: The pages Hugo publishes must be the same set the validator passed;
  procedure dates describe records rather than publication schedules.
- Rejected :: Copying or symlinking sources, host-specific ~baseURL~ values,
  and Hugo's default scheduling were rejected.

** Fetch a pinned standalone Pagefind binary

- Decided :: Cache Pagefind 1.5.2 under ~.tools/~ and verify both the release
  archive and extracted binary with repository-pinned SHA-256 values.
- Why :: The build needs reproducible search without pip or npm, and cached
  builds should not require the network.
- Rejected :: PyPI, npm, shell-only extraction, checksums fetched from the
  same release, and downloading on every build were rejected.

** Serve the built files on loopback with Python

- Decided :: Preview ~public/~ with ~python3 -m http.server~ on
  ~127.0.0.1:8000~, with an optional port override.
- Why :: Pagefind needs HTTP, the server is already available, and loopback
  keeps confidential procedures off the local network.
- Rejected :: Pagefind's fixed-port server, Hugo's server without the index,
  required Caddy, and binding to ~0.0.0.0~ were rejected.

** Allocate IDs from current trees and available history

- Decided :: Make ~new~ choose one above the highest ID in sources, exports,
  and available Git history, then create the filled file exclusively.
- Why :: Gaps may represent deleted procedures, and exclusive creation stops
  an existing file from being overwritten.
- Rejected :: Reusing the lowest gap, a committed counter, and interactive
  slug prompts were rejected as unsafe or conflict-prone.

** Keep dependency checks explicit and output concise

- Decided :: Report required and optional tools without installing them, run
  Hugo and Pagefind quietly, and keep detailed Emacs output in
  ~build/export.log~ unless export fails.
- Why :: The operator sees stable progress lines and one Fedora install
  command without granting the build package-manager authority.
- Rejected :: Automatic installation, one install command per missing tool,
  and noisy successful tool output were rejected.

** Validate current exports and keep hooks optional

- Decided :: Make normal validation export first, pass explicit validator
  arguments through without export, and provide an optional pre-commit hook.
- Why :: The normal verdict must cover current Org sources, while fixtures
  need direct validator access and repository owners retain control of hooks.
- Rejected :: Validating stale exports, adding a fixture-only subcommand, and
  enabling the hook automatically were rejected.

* Site and search

** Use a template for each page kind

- Decided :: Give home, procedure, list, taxonomy, term, search, and date-list
  pages their own Hugo templates, with shared partials for repeated pieces.
- Why :: Hugo already selects templates by page kind, and separate files keep
  unrelated branches out of one large layout.
- Rejected :: One conditional ~list.html~ and hard-coded taxonomy titles were
  rejected.

** Separate base, screen, and print CSS

- Decided :: Build fingerprinted base, screen, and print stylesheets with
  Hugo Pipes, and keep dark-mode and screen overflow rules out of print.
- Why :: Browsers avoid stale assets, and WeasyPrint receives only properties
  and media rules it supports.
- Rejected :: Static unfingerprinted CSS, one mixed-media stylesheet, inline
  CSS, Sass, and PostCSS were rejected.

** Follow the system colour scheme and remain usable on phones

- Decided :: Use contrast-tested light and dark tokens selected by
  ~prefers-color-scheme~, about a 70-character reading measure, and
  independently scrolling wide tables on screen.
- Why :: The site remains readable without a theme control and avoids
  sideways page scrolling at phone width.
- Rejected :: A JavaScript theme toggle, ~light-dark()~, and a separate dark
  stylesheet link that could affect printing were rejected.

** Provide two static procedure orders

- Decided :: Publish ~/procedures/~ by ID and ~/procedures-by-date/~ by
  creation date, newest first, with links between them.
- Why :: Both views work without JavaScript and can share the same procedure
  table partial.
- Rejected :: Client-side sorting, both orders on one page, a nested URL, and
  a custom output format were rejected.

** Use Pagefind's default search UI over HTTP

- Decided :: Use the Pagefind UI on ~/search/~, pass the home page's ~q~
  parameter into it, and show browse links when JavaScript is unavailable.
- Why :: The provided UI already supplies accessible input, filters, result
  paging, and keyboard behavior; serving over HTTP lets it load its index.
- Rejected :: The component UI lacks query normalization, and a custom UI or
  second search engine would add avoidable JavaScript.

** Index the procedure record, not page chrome

- Decided :: Put the metadata panel, structure, and procedure body inside the
  single indexed article, while keeping navigation, banners, and actions
  outside it; preserve HTML whitespace during minification.
- Why :: Search can find IDs, CAS numbers, tags, authors, and body text without
  ranking repeated page furniture or joining metadata labels to values.
- Rejected :: Duplicated hidden metadata, metadata-only Pagefind fields, and
  disabling minification were rejected.

** Implement SMILES search as normalized text substrings

- Decided :: Index every suffix of the punctuation-stripped SMILES in a
  hidden Pagefind metadata field and normalize each query word to letters and
  digits.
- Why :: Pagefind performs prefix search, so suffixes make every normalized
  substring findable without presenting index data in excerpts.
- Rejected :: Extra included punctuation, n-grams, hidden body text, encoded
  punctuation, and a separate JSON search were rejected.

** Expose readable filters

- Decided :: Filter on visible status, reaction-type label, tag, and author
  elements, using human-readable group names and values.
- Why :: Pagefind displays filter values verbatim, and each visible element
  supplies exactly one value.
- Rejected :: Slugs, underscore-separated keys, list-level attributes, and
  duplicate hidden filter spans were rejected.

** Compute precursor links in both directions in Hugo

- Decided :: Render the declared ~precursors~ and derive each reverse
  *Used in* list from all procedure pages at build time.
- Why :: Hugo can compute the relation directly, and the resulting content
  works without JavaScript.
- Rejected :: A precursor taxonomy, a generated reverse-index data file, and
  client-side links were rejected.

** Trigger the sample warning from its tag

- Decided :: Show the sample-data banner whenever ~sample-data~ is among the
  tags, including in print.
- Why :: The existing tag states exactly that the quantities are not
  experimentally verified.
- Rejected :: Using ~status = "draft"~ would mark real drafts as samples, and
  a new flag would change the frozen schema.

** Use safe, printable structure images

- Decided :: Accept SVG or PNG structure images, with shipped SVGs drawn in
  black on a white rectangle, titled, and free of scripts or external
  references; show a screen-only placeholder when absent.
- Why :: The convention stays legible in dark mode and print, scales cleanly,
  and does not fetch or execute outside content.
- Rejected :: Dark-scheme SVG styling and PNG as the sole convention were
  rejected because they can print badly or are not hand-editable vectors.

** Require identical output from Org and Markdown

- Decided :: Test a twin procedure written once in each format and require
  byte-identical pages after substituting their IDs and slugs.
- Why :: Authors should get the same site behavior whichever supported
  source format they use.
- Rejected :: Comparing only the two different seed procedures' element
  shapes was rejected because it would prove little.

* Print and PDF

** Generate PDFs through the main build command

- Decided :: Make ~pdf~ a ~build.fish~ subcommand that rebuilds first and
  names each output after its source file.
- Why :: The PDFs then come from current validated pages and retain the
  recognizable ~OSDB-NNNN-short-slug.pdf~ name.
- Rejected :: A separate script, slug-only names, a running HTTP server, and
  printing whatever is already in ~public/~ were rejected.

** Target WeasyPrint with a browser fallback

- Decided :: Use A4 print CSS with black text, white backgrounds, running ID
  and title headers, page-number footers, and page-break controls; accept
  browser printing without CSS margin-box headers or page numbers.
- Why :: WeasyPrint 70.0 supports the required margin boxes, while the same
  stylesheet still gives browsers a complete, readable printout.
- Rejected :: JavaScript headers, duplicated print templates, ~string-set~,
  and shrinking wide tables were rejected as unsupported or fragile.

** Print a configurable full URL

- Decided :: Build the printed URL from ~params.siteurl~, defaulting to
  ~http://127.0.0.1:8000~, and allow ~HUGO_PARAMS_SITEURL~ to replace the
  origin for deployment.
- Why :: Every fresh build prints a full URL without committing an internal
  deployment host; browser printing can replace it with the current address.
- Rejected :: A path-only default and a committed internal host name were
  rejected.

** Combine automated print checks with visual review

- Decided :: Check page geometry, unsplit rows and steps, and the absence of
  clipping CSS automatically, then inspect rendered page images for the
  remaining clipping risks.
- Why :: PDF text extraction can still report text hidden inside a clipped
  box, and it cannot prove that graphics are visible.
- Rejected :: Source-text comparison, pixel comparison without an independent
  reference, and claiming text extraction proves no clipping were rejected.

* Samples

** Ship eight visibly marked samples and three chains

- Decided :: Ship six Org and two Markdown draft samples, all tagged
  ~sample-data~, across at least five reaction types, with three two-step
  precursor chains.
- Why :: The set exercises both authoring formats, taxonomies, banners,
  search, and precursor links in both directions.
- Rejected :: A camphor sequence, a cinnamate round trip, and extending the
  salicylic-acid seed chain were rejected as hazardous, repetitive, or
  circular choices.

** Prefer verifiable, lower-hazard textbook chemistry

- Decided :: Use procedures whose product CAS numbers resolve by name on
  PubChem and replace the unverified acetate proposal with cinnamic acid.
- Why :: Every sample must be findable by CAS number and suitable as benign
  textbook material.
- Rejected :: Boc protection was dropped because its reagent is fatal if
  inhaled, and the acetate was dropped because its CAS number could not be
  verified.

** Include samples that exercise layout limits

- Decided :: Give one sample a safe SVG structure image and make another a
  long, multi-page procedure with a naturally wide six-column reagents table.
- Why :: The shipped content then exercises the image, responsive-table, and
  multi-page print behavior in normal builds and tests.
- Rejected :: Adding artificial table columns was rejected; the table keeps
  the six columns required of every procedure and gets its width from real
  cell content.
