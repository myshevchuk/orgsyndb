* Start from a generated stub

  Create an Org procedure, from inside its collection, with:

#+begin_src sh
  orgsyndb new "Product name"
#+end_src

  The command chooses the next free identifier across the Org sources,
  Markdown sources, existing exports, and available Git history. It creates
  a file such as ~org/procedures/OSDB-0003-product-name.org~ and fills its
  identifier, slug, title, and current Europe/Berlin timestamps.

  The stub records no AI model. To record an assisting model, add
  ~#+AI_MODEL: example-model-1~ by hand. The command creates the file
  exclusively and never overwrites an existing file. It prints a warning if
  Git history is unavailable or the clone is shallow, because it may then be
  unable to see a deleted identifier.

  The source template is [[file:../templates/procedure.org][templates/procedure.org]]. The complete field rules
  are in [[file:SCHEMA.md][the procedure schema]].

* Understand the template header

  The template describes a /specific procedure/, one run. For a shared
  method applied to several substrates, use a /general procedure/, as
  explained below.

  Org keyword lines start at column zero. Keep every required keyword once,
  and do not indent it.

  - ~#+TITLE~ :: The product name or general method shown as the page title.
  - ~#+CREATED~ :: When the procedure was first written, as an inactive Org
    timestamp.
  - ~#+LAST_MODIFIED~ :: When the procedure was last changed. Update this by
    hand after every change; no command updates it automatically.
  - ~#+AI_MODEL~ (optional) :: The identifier of a model that assisted. Omit
    the line or use ~none~ to record no model.
  - ~#+OPTIONS: author:nil~ :: Prevents Org authorship metadata from becoming
    an invalid ~author~ field in the export.
  - ~#+HUGO_SLUG~ :: The lowercase procedure identifier, such as
    ~osdb-0003~.
  - ~#+HUGO_TAGS~ :: Space-separated tags. Use lowercase letters and digits
    with single hyphens. The ~sample-data~ tag adds a warning banner on
    screen and on paper, so never use it for a real procedure.
  - ~#+HUGO_CUSTOM_FRONT_MATTER~ :: Repeated lines that supply the procedure
    identifier, authors, status, reaction type, scale, products with their
    yields, hazards, and optional fields.

  For a specific procedure, set ~:products~ to a quoted list with one entry per
  product. Each entry contains its ~compound~ key and ~yield_percent~. A key is
  the name of a file in the collection's ~compounds/~ without ~.toml~. Keep
  ~:products~ alone on the last custom-front-matter line. The exporter also
  keeps table-valued metadata last so later fields do not become members of the
  last ~[[products]]~ table.

  Name starting materials in an optional ~:substrates~ line before
  ~:products~. For example:

#+begin_src org
  #+HUGO_CUSTOM_FRONT_MATTER: :substrates '("methyl-salicylate")
  #+HUGO_CUSTOM_FRONT_MATTER: :products '(((compound . "salicylic-acid") (yield_percent . 80)))
#+end_src

  To add another product, add another entry of the form
  ~((compound . "key") (yield_percent . N))~ inside the outer list. Every
  yield is a number from 0 to 100 without quotes or ~%~. Do not list a key
  twice in either list or list a product as a starting material.

  The site links the starting materials to their compound pages. It derives
  *Precursors* from other procedures that make those compounds and
  *Used in* from procedures that start from your products. You do not write
  these procedure links yourself; they work across procedure languages.

  Put all tags on the ~#+HUGO_TAGS~ line, separated by spaces:

#+begin_src org
  #+HUGO_TAGS: esterification fragrance
#+end_src

  Product names, chemical data and structure images belong in the compound
  registry described next, rather than in the procedure header.

  Use the template's quoting and list forms. For example, authors and hazards
  use quoted Lisp lists such as ~'("A. Example" "B. Example")~. Consult
  [[file:SCHEMA.md][docs/SCHEMA.md]] for the exact required values, optional fields, reaction
  vocabulary, and file-name rules.

  For a general procedure, replace the top-level ~:products~ and ~:substrates~
  with a named scope table, as shown below. Keep ~:scale~ as the typical scale.

* Find or add the compounds

  The /compound registry/ is the collection's ~compounds/~ folder. One
  ~<key>.toml~ file describes each compound, shared by every procedure that
  makes or uses it. Look for an existing entry first. The key identifies
  the compound; the site does not compare structures to find duplicates.

  For a new compound, copy
  [[file:../templates/compound.toml][templates/compound.toml]] into ~compounds/~.
  Choose a file name with lowercase letters and digits separated by single
  hyphens, such as ~ethyl-acetate.toml~. Use ~ethyl-acetate~ as the key in
  ~:products~ or ~:substrates~. Replace the stub's ~example-compound~ key
  with the key you actually use. Creating a procedure stub does not create
  compound records.

  The compound file is TOML, even when your procedure is Org. It has no
  ~+++~ lines or ~[product]~ heading. Fill in ~name~, ~formula~, ~mw~ in
  g/mol, and ~smiles~, a text notation for molecular structures. Text uses
  double quotes; molecular weight is a positive number without quotes.
  The optional ~name_de~ supplies the name on a German site; without it,
  that site uses ~name~. An English site always uses ~name~. You may also
  add ~cas~, the CAS Registry Number, and ~structure_image~.

  To show a structure, place an SVG or PNG file in the collection's
  ~static/structures/~. Set ~structure_image~ in the compound file, for
  example ~structure_image = "structures/isopentyl-acetate.svg"~ for
  ~isopentyl-acetate~. A structure SVG uses black lines and text on a white
  background rectangle. It includes a ~<title>~ and contains no scripts,
  external images, or other external references. The white background
  keeps the drawing legible on the site's dark colour scheme and on paper.

  You may register a starting material even if no procedure makes it. A
  compound that no procedure uses is also allowed. *Compounds* in the site
  navigation opens ~/compounds/~. Each name links to a page with chemical data,
  the structure when supplied, *Made by* procedures with yields and status, and
  *Used in* procedures with status. A general procedure appears under *Made by*
  once per entry that makes the compound, as
  ~<ID> <title> · entry <n> · <yield> % · <status>~. *Used in* lists each
  procedure once; the directory also counts each procedure once.

* Write a general procedure

  When one method covers several substrates, write it once as a /general
  procedure/. Its ~scope~ records each application of the method, with its
  starting materials, products and yields. The presence of ~scope~ makes the
  procedure general; do not add a ~kind~ field.

  Remove the template's top-level ~:products~ and ~:substrates~ lines. Keep all
  other required fields, including ~:scale~ for the typical scale. Write one
  Org table directly after ~#+NAME: scope~, anywhere outside a block. The table
  name is case-insensitive. The first row names the columns; follow it with a
  separator line and one row per entry. This excerpt from the export fixture
  shows an entry with two products:

#+begin_src org
  #+NAME: scope
  | substrates          | products                     | yield_percent | time   | temperature | note       |
  |---------------------+------------------------------+---------------+--------+-------------+------------|
  | acetic-acid ethanol | ethyl-acetate propyl-acetate | 45,5 30       | 2 h    | 80          | Reflux     |
  | acetic-acid         | benzyl-acetate               | 78            |        | 25          | Stir only  |
  | ethanol             | methyl-benzoate              | 72,5          | 30 min | 60,5        | Two phases |
#+end_src

  The required columns are ~substrates~, ~products~ and ~yield_percent~.
  Separate compound keys by spaces, and give one yield per product, in product
  order, also separated by spaces. Yields are numbers from 0 to 100 without
  ~%~. Each entry needs at least one starting material and product. Within an
  entry, do not repeat a key or list a product as a starting material. A
  compound may be a starting material in one entry and a product in another.
  Entries are numbered from 1 in row order.

  Optional columns are ~scale~, ~time~, ~temperature~ and ~note~. Scale is text
  with a number and unit, such as ~5 mmol~. Time is a number followed by ~min~,
  ~h~ or ~d~, such as ~30 min~. Temperature is one number in °C, without a
  unit. Note is text. Numbers in the table may use a decimal comma, as ~45,5~
  does above. An empty cell leaves its key unset; required entry fields are
  still checked by validation. Keep column names English in every language.

  Export writes ~scope~ front matter and removes the table and its ~#+NAME~
  line from the exported body. Keep the eight body headings and describe the
  shared method there. The complete
  [[file:../tests/fixtures/export/OSDB-0909-scope-table.org][Org fixture]]
  shows this table in a procedure. The demo's ninth procedure,
  [[file:../examples/demo/md/procedures/OSDB-0009-benzylic-alcohols.md][OSDB-0009]],
  shows the same scope data format in Markdown for three aryl methyl ketones
  reduced with sodium borohydride. These are sample data, not experimentally
  verified procedures.

  To show the overall reaction, place an SVG or PNG under ~static/structures/~
  and add:

#+begin_src org
  #+HUGO_CUSTOM_FRONT_MATTER: :scheme_image "structures/aryl-ketone-reduction.svg"
#+end_src

  The path must start with ~structures/~, contain no ~..~ component and name an
  existing ~.svg~ or ~.png~ file under ~static/~. Any procedure may set
  ~scheme_image~; it replaces product structures in the title block. A general
  procedure without it shows *No structure image*.

* Understand the finished page

  The labels below are those of an English site; a German site, the default,
  shows them in German, such as *Kopieren* for *Copy*. The title block shows
  the procedure ID and a status badge above ~#+TITLE~. When ~:status~ is
  ~checked~ and ~:checked_by~ is set, the checkers' names follow the badge, so
  the line reads *checked by* followed by the names. Under the title, ~:scale~
  appears as *Scale* and product yields as *Yield*. For a specific procedure,
  one product shows only its percentage; several show a percentage and compound
  name for each, in product order. The *Print / Save as PDF* button follows
  them. A general procedure shows the typical top-level scale and the yield
  range over all products of all entries, ~<min>–<max> %~, or one percentage
  when all yields are equal.

  Without ~scheme_image~, a specific procedure shows one structure figure per
  product whose compound has an image, in product order. On a wide screen, the
  figures sit to the right of the title, above the metadata panel. In a narrow
  window they follow the print button, before the panel. In print they also
  precede the panel. When neither a scheme nor product figures are shown, the
  screen shows a *No structure image* placeholder, which is omitted from
  printouts. A rule closes the title block on screen.

  The metadata panel always links the product names to their compound pages
  under *Product* or *Products*, even when a name equals the title. For one
  product it also shows formula, molecular weight, CAS when set, and SMILES.
  For several products, find those data on their compound pages. *Starting
  materials* links the compounds in ~:substrates~. For a general procedure,
  both lists include all entries, each compound once in order of first
  appearance. Precursor and used-in links consider every entry. The panel then
  shows reaction type, tags, authors, checkers when set for draft or retired
  procedures under *Checked by*, created and modified times, and precursor or
  used-in links. Formula digits appear as subscripts. Molecular weight gains
  ~g/mol~, yield gains a percent sign, and SMILES has a *Copy* button. Reaction
  type, tag, and author values link to pages that list related procedures. The
  site title-cases author names for display, so ~van~ appears as ~Van~. The
  eight body sections appear beside the panel on a wide screen and after it in
  a narrow window or in print.

  A general procedure adds *Scope* before *Summary*, one row per entry. The
  columns *Entry*, *Starting materials*, *Products* and *Yield* always appear.
  *Scale*, *Time*, *Temperature* and *Note* appear only when some entry sets
  the field; unset values leave empty cells. Compounds link to their pages, and
  products show small structure images when their registry records have them.
  Entry 1 of OSDB-0009 makes the same alcohol as OSDB-0005, so its compound
  page lists both routes.

* Use exact timestamps

  ~#+CREATED~ and ~#+LAST_MODIFIED~ use this exact form:

#+begin_example
  [YYYY-MM-DD Day hh:mm:ss]
#+end_example

  Use Europe/Berlin local wall-clock time, an English three-letter weekday,
  and seconds. Org timestamps do not carry the UTC offset. The exporter adds
  the Berlin offset in force at that instant. A time skipped during the
  spring clock change is invalid. During the repeated autumn hour, export
  uses the earlier summer offset for ~#+CREATED~.

  ~orgsyndb new~ supplies valid timestamps and English weekday names.
  For timestamps inserted interactively by Emacs, make its time locale
  English:

#+begin_src emacs-lisp
  (setq system-time-locale "C")
#+end_src

  Keep ~#+CREATED~ unchanged. Set ~#+LAST_MODIFIED~ to the current local time
  whenever you change the procedure. It must not be earlier than
  ~#+CREATED~. See [[file:SCHEMA.md][the procedure schema]] for the exact validation rules
  around clock changes.

* Write the body

  Keep these top-level headings in this order:

  1. Summary
  2. Reagents
  3. Procedure
  4. Workup and Purification
  5. Characterization
  6. Notes
  7. Hazards and Waste Disposal
  8. References

  Use one leading star for each of these headings. Lower-level headings may
  use more stars. Use an Org table for reagents and numbered lists for steps
  and notes. Include quantities, temperatures, times, observations, workup,
  purification, characterization, hazards, and waste handling. Write
  ~None.~ under References when there is no reference.

  To let readers jump from a step to a note, number the notes as an ordered
  list under Notes. In the Org body, write a reference as plain text
  ~(Note 2)~: the word ~Note~, a space and the number, in parentheses.
  After export, the site links it to note 2 if that note exists. Forms
  such as ~(Notes 2 and 3)~, ~(Note 2a)~ and ~see Note 2~ stay plain text.
  References inside source blocks or inline code are not linked.

  Keep the Reagents table's six columns in this order: ~Reagent~, ~CAS~,
  ~MW (g/mol)~, ~Amount~, ~mmol~, and ~Equiv~. A wide table scrolls sideways
  inside its own area on screen and wraps to fit the paper when printed.

  Write chemical subscripts and superscripts with braces:

#+begin_example
  H_{2}O
  10^{-3}
#+end_example

  Plain ~CO_2~ stays plain text. Dollar-delimited text such as ~$x$~ and
  LaTeX delimiters such as ~\(y^2\)~ also stay literal because the site has
  no math renderer.

  The sample [[file:../examples/demo/org/procedures/OSDB-0001-salicylic-acid.org][OSDB-0001-salicylic-acid.org]] in the demo collection
  shows the expected structure. It is sample data, not an experimentally verified procedure.

* Export, validate, and preview

  Export Org sources with:

#+begin_src sh
  orgsyndb export
#+end_src

  Before exporting anything, the command checks Org file names, the required
  file-level keywords, the named scope table, and routes that could set the
  exported dates, AI model, or file name. It reports each problem as
  ~<path>:<field>: error|warning: <message>~, the same line format as the
  validator. An error stops the export and leaves ~build/export/~ unchanged.

  A malformed scope table reports field ~scope~ and stops export. These
  messages identify the source problem; row numbers start at 1 after the
  separator:

  | Message | Correction |
  |---------+------------|
  | ~appears more than once~ | Keep one table named ~scope~. |
  | ~"<name>" is not a scope column~ | Use one of the seven column names. |
  | ~column "<name>" missing~ | Add the required column. |
  | ~column "<name>" appears more than once~ | Keep the column once. |
  | ~row <n>: <p> products but <y> yields~ | Give one yield per product in order. |
  | ~row <n>: "<cell>" is not a number~ | Write a numeric yield or temperature without units. |

  Export runs Emacs in an isolated batch environment. It does not load or
  write the owner's Emacs configuration. On the first run it fetches pinned
  copies of ox-hugo and tomelr into the application's ~.emacs-batch/~.
  Exported Markdown goes to the collection's ~build/export/~, and Emacs
  output goes to ~build/export.log~.

  An Org check error, another Emacs failure, and an ~org/procedures~ that is
  not a directory produce these messages, respectively. For the second
  case, the command prints the log first.

#+begin_example
  orgsyndb: error: the Org sources have errors; build/export/ is unchanged
  orgsyndb: error: export failed; Emacs output is in build/export.log
  orgsyndb: error: org/procedures is not a directory
#+end_example

  Org files remain the source of truth. Do not edit ~build/export/~. Each
  export rebuilds the complete directory, removes orphaned exports, and
  produces byte-identical output when the sources and tool versions have not
  changed.

  The export has deliberate limits:

  - It does not render LaTeX or dollar-delimited mathematics.
  - It interprets only braced Org subscript and superscript forms.
  - It never evaluates source blocks.
  - It ignores file-local variables.

  Check the Org sources, all exported or hand-written Markdown and the
  compound registry with:

#+begin_src sh
  orgsyndb validate
#+end_src

  ~orgsyndb validate~ runs the export first. If the export reports an Org
  error, validation stops there and does not start the Markdown validator.
  Otherwise, errors in procedures or compound records fail validation and
  warnings do not. The command uses the collection's ~compounds/~ registry and
  ~static/~ for images. A field such as ~products[1].yield_percent~ names the
  yield in the first product entry; counting starts at 1. ~unknown compound~
  means you must check the key and its registry file. Registry problems name
  the compound file and its field, such as ~compounds/ethyl-acetate.toml:mw~.
  The summary counts compound files too. For scope entries, ~scope[2].time~
  means the time in entry 2; ~scope[2].products[1].yield_percent~ means that
  entry's first product yield. ~must not be empty~ under ~scope~ requires at
  least one entry. A top-level field with
  ~a general procedure lists them in scope; move <key> into its entries~ must
  be moved into the relevant entries. Time errors ask for a number followed by
  ~min~, ~h~ or ~d~; temperature errors ask for an unquoted number in °C. The
  schema explains every field and the validator's exit statuses.

  Build and preview the site with:

#+begin_src sh
  orgsyndb serve
#+end_src

  Open http://127.0.0.1:8000/ after the command prints that it is serving.
  The server is reachable only from the same machine. It has no live reload,
  so stop it with ~Ctrl-C~ and run it again after an edit.

  On a procedure page, choose *Print / Save as PDF* to open the browser's
  print dialog. The print layout is complete A4 output in black on white.
  Firefox omits the running header and page numbers that WeasyPrint adds to
  PDFs created by ~orgsyndb pdf~.

  To find general procedures, use the catalogue's *Kind* filter: *Specific
  procedure* or *General procedure*. Its tabs are *All procedures*, *General
  procedures*, *Reaction types*, *Tags* and *Authors*. *General procedures*
  opens ~/general-procedures/~, a catalogue restricted to general procedures,
  with the header search labelled *Search general procedures*. *Only general
  procedures · Browse all procedures* links to the full catalogue. *Clear all*
  keeps the restriction; *Browse all procedures* removes it and carries the
  query, other filters, sort and view. In the full catalogue, ~kind=general~ in
  the address selects this kind. Without JavaScript the general-procedures page
  still lists its procedures by ID. Catalogue *Details* includes all entries'
  products and the yield range.

* Write in German or translate

  The site has one language, set by ~locale~ in the application's
  ~site/hugo.toml~: ~"de"~ by default, or ~"en"~. A file name may carry a
  language code before its suffix, ~.de~ or ~.en~; files with the same ID
  are variants of one procedure. Every procedure is published once: the
  variant tagged with the site's language, else the one without a code,
  else one tagged with the other language. Create a German stub with:

#+begin_src sh
  orgsyndb new --lang de "Produktname"
#+end_src

  It fills [[file:../templates/procedure.de.org][templates/procedure.de.org]] and names the file
  ~OSDB-NNNN-produktname.de.org~. Umlauts and ß in the title are written
  out in the slug: ~Größe~ becomes ~groesse~. The German body uses these
  top-level headings, in this order: Zusammenfassung, Reagenzien,
  Durchführung, Aufarbeitung und Reinigung, Charakterisierung,
  Anmerkungen, Gefahren und Entsorgung, Literatur. Its Reagents table has
  the columns ~Reagenz~, ~CAS~, ~M (g/mol)~, ~Menge~, ~mmol~ and ~Äquiv.~,
  and its text uses decimal commas. Org keywords, custom-front-matter keys,
  status values, reaction-type slugs and tags stay English, and so do the
  weekday names in ~#+CREATED~ and ~#+LAST_MODIFIED~.

  Use the [[file:STYLE.de.md][German procedure style guide]] for the wording
  and the [[file:GLOSSARY.de.md][German organic-synthesis glossary]] for terms,
  fixed phrases, reusable sentences, and their English equivalents.

  A file without a code may use the English or the German headings. To
  state its language, add a custom-front-matter line, before ~:products~
  in a specific procedure:

#+begin_src org
  #+HUGO_CUSTOM_FRONT_MATTER: :language "de"
#+end_src

  On a tagged file the field must name the code's language; the build adds
  it when it is missing. A page whose procedure is in another language than
  the site carries a ~lang~ attribute.

  To translate a procedure, copy ~OSDB-0001-x.org~ to ~OSDB-0001-x.de.org~ and
  translate the title, the hazards, the references if needed, and the body. Set
  both timestamps to the time of the translation. Leave ~:status~,
  ~:reaction_types~, ~#+HUGO_TAGS~, ~:products~, ~:substrates~ and
  ~:scheme_image~ unchanged. Keep the scope table's entry order and all values
  except ~note~, which you translate. The validator compares the shared fields
  with the original and reports differences as errors. Numeric yields compare
  by value, so ~85~ and ~85.0~ agree. Compound names come from ~name~ and
  ~name_de~ in the shared registry; add or edit ~name_de~ there for the German
  name. The original and its translation may use different formats.

  The export keeps the language code: ~OSDB-0001-x.de.org~ becomes
  ~build/export/OSDB-0001-x.de.md~. On a German site it is published at
  ~/procedures/osdb-0001/~ in place of ~OSDB-0001-x.org~, and ~orgsyndb pdf~
  prints it to ~pdf/OSDB-0001-x.de.pdf~ with a German page footer.
  [[file:SCHEMA.md][The procedure schema]] gives the exact rules.
